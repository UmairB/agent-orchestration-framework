# Phase 9 Wave 2 Plan: Package Resolution And Lock Metadata

## Objective

Record direct resolved package metadata in `.aof/aof.lock.json` while preserving the existing GSD installer preview, network boundary, install attempt history, and lock replay behavior.

## Planning Assumptions

- Dry-run and non-install sync paths must not fetch npm/git sources.
- Exact pinned npm versions, git refs, and local file paths can be recorded deterministically.
- Tags/ranges such as `latest` should be represented honestly as requested selectors unless an explicit installer path supplies resolved metadata.
- Existing `frameworks` lock entries should remain compatible with current replay tests while new `packages` entries carry richer metadata.

## Requirements Covered

- **PKG-01:** Package source descriptors feed install planning for npm, git, and local file sources.
- **PKG-03:** Lock state records direct dependency metadata and resolved package metadata.

## Tasks

1. Add resolved package metadata helpers.
   - Extend `src/packages.mjs` with `resolvedPackageEntry(pkg, options)`.
   - Include `id`, `namespace`, normalized `source`, `resolved`, `dependencies`, `runtimes`, `scope`, `intent`, and `generatedAt`.
   - Represent exact pinned sources deterministically.
   - For non-concrete npm tags/ranges, include a clear resolution status instead of fabricating a concrete version.

2. Update framework install planning to use normalized sources.
   - Replace ad hoc `sourceToPackageName()` behavior with `packageInstallSpec()` or equivalent.
   - Keep existing command shape for `npm:get-shit-done-cc@latest`.
   - Support git/file install specs in dry-run output without running network/file installers.
   - Preserve skip logic based on matching prior successful install attempts.
   - Include namespace where useful in plan items and attempts without breaking existing fields.

3. Extend lock manifests.
   - Update `createLockManifest()` to include a `packages` array using resolved package entries.
   - Preserve `frameworks` for compatibility with existing tests and `install --from-lock`.
   - Preserve `frameworkInstallAttempts` history.
   - Ensure drift-warning preservation of `files` does not drop package metadata.

4. Update lock replay.
   - Make `frameworkPlanFromLock()` prefer new package lock entries where available.
   - Fall back to existing `frameworks` lock entries for older locks.
   - Keep `install --from-lock --dry-run` behavior stable for current GSD locks.

5. Surface package lock details in plan previews and diagnostics.
   - Update `summarizeLockManifest()` to include package count if useful while preserving existing summary fields.
   - Update `doctorConfig()` package-intent details to include namespace, source type, dependency count, and runtimes.
   - Update JSON dry-run payloads only additively.

6. Add tests for lock and installer compatibility.
   - Unit test resolved lock entries for npm, git, and local file descriptors.
   - Unit test direct dependencies are written into lock package metadata.
   - Unit test existing framework replay still works from old `frameworks` entries.
   - Unit test `install gsd --dry-run` and `sync --dry-run` preserve current npm command output.
   - BDD test lock state contains package `gsd` with namespace and source metadata after `apply` or `sync`.

## Acceptance Criteria

- Lock manifests include direct resolved package metadata.
- Existing `frameworks` and `frameworkInstallAttempts` behavior remains compatible.
- `sync --dry-run` and `install --dry-run` remain side-effect-free.
- npm/git/file package descriptors can produce installer preview specs.
- Existing GSD package flows still pass with namespace-aware config.
