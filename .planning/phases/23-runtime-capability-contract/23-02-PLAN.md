# Phase 23 Wave 2 Plan: Apply/Render Hard Gate And BDD Coverage

## Objective

Ensure invalid Codex command targeting cannot reach runtime rendering or writes, preserve Claude command rendering, and prove the behavior through user-facing BDD scenarios and render-plan tests.

## Planning Assumptions

- Plan 23-01 has introduced shared validation diagnostics for unsupported runtime capabilities and simple argument markers.
- `aof assets apply` must run validation before render planning because render planning can currently create Codex command outputs directly.
- Stale generated file cleanup should happen only when the current source config is valid.
- Existing lock cleanup behavior should be reused rather than replaced.

## Requirements Covered

- **RTS-01:** Claude command assets render to Claude commands.
- **RTS-02:** Codex command targets are rejected.
- **RTS-03:** Apply-time diagnostics are clear and block writes.
- **SIMPLE-01:** Simple assets still render directly without workflow files.
- **SIMPLE-02:** Simple argument configuration is rejected before apply.
- **SIMPLE-03:** Argument marker guidance is visible through CLI validation/apply flows.

## Decisions Covered

- **D-01..D-03:** Claude-only command rendering, Codex rejection, no command-to-skill mapping.
- **D-06..D-10:** Apply fails before writes for invalid config and cleanup happens only after config is fixed.
- **D-11..D-13, D-15:** Simple assets remain direct and argument-free.
- **D-16:** CLI diagnostics, render behavior, unit tests, and BDD coverage are updated.

## Tasks

1. Add apply preflight validation in `src/cli.mjs`.
   - In `assetsApplyCommand()`, call `validateConfig(targetDir, options)` after resolving the target/config path and before collecting adapter warnings or creating render plans.
   - If validation errors exist, print the same style of diagnostics as `aof project validate` or factor a small helper so apply output remains consistent.
   - Set `process.exitCode = 1` and return before any writes, lock updates, or dry-run render output.
   - Preserve strict adapter-warning behavior for configs that pass validation.

2. Add a defensive render guard in `src/adapters.mjs`.
   - Prevent direct `renderConfigOutputs()` or `createRenderPlan()` calls from rendering `kind: "command"` for `runtime === "codex"`.
   - Throw a clear error if a caller bypasses validation.
   - Keep Claude command rendering and command associated-file rendering unchanged.

3. Verify stale Codex command cleanup after config correction.
   - Add a render-plan or CLI-level test where the previous lock contains `.codex/commands/ci.md` and the corrected desired outputs no longer include it.
   - Confirm `planApplyActions()` produces a `delete` action for the stale lock-owned Codex command file when it is unmodified.
   - Confirm modified stale files remain drift-protected.
   - Do not add a special cleanup path that runs when validation fails.

4. Add user-facing BDD scenarios.
   - Codex command validation:
     - Given a project with a Codex command asset.
     - When `project validate` or `assets validate` runs.
     - Then the command fails with a message that command assets are not supported for Codex.
   - Codex command apply rejection:
     - Given the same project.
     - When `assets apply --codex` runs.
     - Then the command fails and `.codex/commands/<id>.md` does not exist.
   - Claude command rendering:
     - Given a project with a Claude-only command asset.
     - When `assets apply --claude` runs.
     - Then `.claude/commands/<id>.md` exists and `.codex/commands/<id>.md` does not exist.
   - Simple argument marker:
     - Given a simple asset body with `$ARGUMENTS` or `{{GSD_ARGS}}`.
     - When validation runs.
     - Then validation fails with workflow-backed argument guidance.

5. Keep PowerShell parity.
   - Update `test/integration/cli.ps1` only if the shared feature runner needs new step support.
   - Run PowerShell BDD after Node BDD to catch platform path/output differences.

6. Update docs/help where Phase 23 behavior is user-visible.
   - Update README sections that mention command runtimes so they state commands are Claude-only and Codex behavior should be authored as skills.
   - Mention simple assets do not support arguments and workflow-backed argument support is planned for the workflow model.
   - Avoid documenting `{{skills.*}}` or `{{workflows.*}}` until later phases implement them.

## Acceptance Criteria

- `aof assets apply --codex` fails before writing when config includes a Codex command resource.
- Direct render planning cannot produce `.codex/commands/*`.
- `aof assets apply --claude` renders Claude command assets to `.claude/commands/<id>.md`.
- Existing simple skill, rule, and agent rendering remains unchanged.
- After a config is corrected to remove Codex command targeting, lock-owned stale `.codex/commands/*` can be deleted by normal apply planning.
- Node BDD and PowerShell BDD cover the new user-visible behavior.

## Verification

- `npm run test:unit`

  - `node bin/aof.mjs assets apply --codex --dry-run` in that fixture.
  - `node bin/aof.mjs assets apply --claude --dry-run` in a Claude-only command fixture.
