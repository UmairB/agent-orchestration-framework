# Phase 5 Wave 2 Plan: Setup UI Request Hardening And Cross-Platform UI Build Wrapper

## Goal

Close setup UI server risks while preserving the Phase 4 configuration editor and old catalog endpoints, then replace the npm workspace UI build path with a Windows-safe Node wrapper that can participate in the final `npm run check` command.

## Requirements Covered

- **VERI-03:** UI configuration editing paths are covered by build checks or targeted tests.

## Decisions Covered

- **D-09:** close request validation and static serving risks.
- **D-10:** attempt lightweight browser smoke if feasible; API and build checks remain fallback.
- **D-11:** keep and harden old catalog endpoints.
- **D-12:** keep local-only defensive setup UI posture.
- **D-17:** add a cross-platform UI build wrapper through Node entry points.
- **D-18:** keep `npm test` focused and make `npm run check` include the wrapper.
- **D-19:** document wrapper and direct Node fallback commands.
- **D-20:** include UI build and `npm run check` in Phase 5 verification.

## Implementation Tasks

1. Centralize setup UI API error responses.
   - Add helper(s) in `src/setup-ui.mjs` for JSON success and JSON error payloads.
   - Use a consistent shape such as `{ ok: false, error, diagnostics? }` for API failures.
   - Keep successful existing payloads backward-compatible where practical.
   - Return deterministic status codes for malformed JSON, validation failures, payload-too-large, unknown API routes, and unsupported methods.

2. Harden JSON body parsing.
   - Replace route-local `JSON.parse()` calls with one `readJsonBody()` helper.
   - Distinguish empty bodies, malformed JSON, oversized bodies, and stream errors.
   - Ensure the body-size guard stops processing deterministically after rejection.
   - Keep the current local request size policy unless tests show it needs a named constant.

3. Harden config editor routes.
   - Validate URL `kind` and `id` for `PUT /api/config/resources/:kind/:id`.
   - Reject route/payload mismatches instead of silently overriding ambiguous input.
   - Continue to rely on `saveEditableResource()` for central save validation.
   - Ensure invalid route kind/id returns a structured JSON error.

4. Harden old catalog endpoints.
   - Keep `GET /api/items` and `POST /api/items`.
   - Validate `POST /api/items` JSON body, `id`, `name`, `kind`, `body`, and `runtimes` at a practical v1 level.
   - Preserve support for the old skill/agent catalog creation flow.
   - Reject unsupported kinds with the existing user-facing constraint made structured.

5. Harden static serving.
   - Keep binding to `127.0.0.1`.
   - Keep static paths constrained inside the `ui/` directory.
   - Handle encoded traversal and invalid percent-encoding without throwing out of the request handler.
   - Add tests for `/`, expected assets or not-found behavior, `../` traversal, encoded traversal, and unknown static files.

6. Expand setup UI server tests.
   - Extend `test/setup-ui.test.mjs`.
   - Cover capabilities, config load/save, malformed JSON, oversized body behavior, invalid config route kind/id, route/payload mismatch, catalog endpoint validation, and static traversal safety.
   - Use local HTTP calls against `serveSetupUi(..., { port: 0 })`.
   - Close servers and clean temp directories in `finally` blocks.

7. Add the cross-platform UI build wrapper.
   - Add `scripts/ui-build.mjs`.
   - From the UI workspace directory, invoke TypeScript with `process.execPath` and the local `typescript/bin/tsc` entry point.
   - Then invoke Vite with `process.execPath` and the local `vite/bin/vite.js` entry point.
   - Inherit stdio and propagate non-zero exit status.
   - Avoid shell-specific command strings.

8. Update package scripts.
   - Change root `ui:build` to `node ./scripts/ui-build.mjs`.
   - Change root `check` to run `npm test` and then the UI build wrapper.
   - Do not change `npm test` to include UI build.
   - Leave `ui/package.json` scripts in place unless a small documentation note is needed.

9. Update docs for build commands.
   - Update README verification/setup UI docs.
   - Document `npm run ui:build` as the primary build check.
   - Document direct fallback commands:
     - `node ..\node_modules\typescript\bin\tsc -b` from `ui/`
     - `node ..\node_modules\vite\bin\vite.js build` from `ui/`
   - Explain that UI writes config only and CLI remains the execution boundary.

10. Attempt lightweight browser smoke if feasible.
   - If local tooling can open the setup UI reliably, run a smoke check that confirms the app loads and can fetch capabilities/config.
   - If browser tooling is unavailable or blocked, record API tests plus UI build as the fallback in the summary.

## Acceptance Criteria

- Setup UI API failures return structured JSON errors.
- Malformed JSON and oversized request bodies are tested.
- Config-resource route validation prevents ambiguous kind/id saves.
- Old catalog endpoints still work for supported v1 input and reject invalid input.
- Static serving rejects traversal safely.
- `npm run ui:build` uses a Node wrapper and avoids the prior Windows npm/Git Bash shim issue.
- `npm run check` runs `npm test` plus the UI build wrapper.
- Documentation names the wrapper as primary and direct TypeScript/Vite commands as fallback.

## Verification

- `npm run test:unit`
- `npm test`
- `npm run ui:build`
- `npm run check`
