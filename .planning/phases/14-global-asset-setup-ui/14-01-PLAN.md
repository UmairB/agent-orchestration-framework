# Phase 14 Wave 1 Plan: Scoped Setup UI Config API

## Objective

Extend the setup UI backend and editable config layer so the API can load and save either project-local `.aof` config or global `~/.aof` config through explicit scope, while preserving existing project endpoints.

## Planning Assumptions

- Existing `/api/config` and `/api/config/resources/:kind/:id` remain project-scoped for backward compatibility.
- New scoped routes can be route-based or query-based, but must encode `project` versus `global` explicitly.
- Global scope uses `globalWorkspacePaths()` from `src/workspace.mjs`.
- Phase 14 exposes global skills, agents, and rules as the user-facing asset kinds.
- Associated-file editing is text-only and skill-only.

## Requirements Covered

- **GUI-01:** User can switch the setup UI between project asset editing and global asset editing.
- **GUI-02:** User can create and edit global skills, agents, and rules through the setup UI.
- **GUI-04:** Setup UI clearly labels asset source scope.

## Decisions Covered

- **D-01..D-04:** Explicit Project / Global scope model and labels.
- **D-05:** Global skills, agents, and rules are supported.
- **D-07:** Reuse file-backed editor conventions.
- **D-13..D-16:** Basic global skill associated-file editing follows Phase 13 path rules.
- **D-17:** API endpoints encode explicit scope.
- **D-19..D-20:** Saves return structured diagnostics and validate the right config.

## Tasks

1. Add scoped editable config helpers.
   - Generalize `loadEditableConfig(projectDir, options)` so it can load `project` or `global` scope.
   - Generalize `saveEditableResource()` so global scope writes to `~/.aof/aof.config.json` and global `assets/...`.
   - Preserve existing project behavior and function signatures where possible.
   - Add a `scope` field to payloads returned by scoped APIs.

2. Expose global resource payloads.
   - Include `source: "project"` or `source: "global"` on editable resources.
   - Filter the primary Global UI/API resource kinds to `skill`, `agent`, and `rule`.
   - Keep commands project-local unless existing generic internals make them unavoidable without surfacing them in the UI.

3. Add associated-file payload support.
   - Extend `EditableResource` payloads with `files` for skill resources.
   - Load listed associated files as `{ path, body }` from the asset directory.
   - Save global skill associated files to the global asset directory.
   - Write the manifest `files` array with explicit relative paths.
   - Reject or return diagnostics for associated files on non-skills, path escapes, primary-body duplication, missing path values, or invalid text payloads.

4. Add setup UI routes.
   - Keep `GET /api/config` and `PUT /api/config/resources/:kind/:id` as project-scoped aliases.
   - Add explicit scoped load and save endpoints, for example `/api/config/project`, `/api/config/global`, and `/api/config/:scope/resources/:kind/:id`.
   - Reject invalid scopes with a structured `invalid-scope` response.
   - Ensure malformed JSON and route/payload mismatch protections still apply.

5. Add unit/API tests.
   - Existing project setup UI API tests continue to pass.
   - Loading global scope returns global config path and `scope: "global"`.
   - Saving a global skill creates `~/.aof` config and global body file.
   - Saving a global skill with associated file writes the helper file and manifest `files`.
   - Saving unsupported scoped kinds or unsafe associated files returns structured diagnostics.

6. Verify wave 1.
   - Run `npm run test:unit`.

## Acceptance Criteria

- Setup UI API can load project and global scope explicitly.
- Existing project setup UI endpoints remain compatible.
- Global skill, agent, and rule assets can be saved through the API.
- Global skill associated files can be saved as explicit text files under the asset directory.
- Save failures return structured diagnostics.
