# Phase 7 Wave 3 Plan: UI Editing And Documentation For Expanded DSL

## Objective

Expose the expanded DSL primitives through the setup UI and public docs so users can create valid configuration without hand-editing JSON, while keeping CLI execution as the only side-effect path.

## Planning Assumptions

- **A-06:** The UI should provide narrow valid-config editing and review visibility for new sections, not a full bespoke builder for every runtime-specific option.

## Requirements Covered

- **DSL-01:** UI/docs show how to define MCP servers.
- **DSL-02:** UI/docs show how to define hooks.
- **DSL-03:** UI/docs show how to define project docs.
- **DSL-04:** UI/docs show how to define settings and runtime escape hatches.
- **DSL-05:** UI/editor changes preserve existing resource editing.

## Tasks

1. Extend editable config payloads.
   - Update `src/config-editor.mjs` so `loadEditableConfig()` returns `mcpServers`, `hooks`, `projectDocs`, and `settings`.
   - Add save/update support for expanded sections through a conservative whole-section API or targeted endpoints.
   - Reuse validation from `src/config-inspect.mjs` before accepting saves.
   - Keep existing resource save behavior unchanged.

2. Extend setup UI API.
   - Update `src/setup-ui.mjs` endpoints to serve and save expanded sections.
   - Preserve payload size limits, JSON parse validation, route validation, and path safety from previous hardening.
   - Return diagnostics in the same shape the Review tab already understands.

3. Add setup UI editing surfaces.
   - Add navigation for MCP Servers, Hooks, Project Docs, and Settings.
   - Use compact forms or structured JSON editors where full bespoke controls would create more complexity than value.
   - Surface runtime capability/status messages for new sections.
   - Keep the Review tab focused on diagnostics, runtime coverage, package intent, and next terminal commands.
   - Do not add browser-executed `apply`, `sync`, `install`, or shell execution.

4. Update CLI/docs examples.
   - Update README with `.aof/aof.config.json` examples for `mcpServers`, `hooks`, `projectDocs`, and `settings`.
   - Document generated outputs and drift behavior for root docs/config files.
   - Document that Phase 7 common hooks are command hooks; richer degradation/warning policy follows in Phase 8.

5. Add tests.
   - Unit/API tests for loading and saving expanded sections.
   - Setup UI tests for malformed expanded-section payloads and route validation.
   - Integration scenario proving a user can define expanded primitives in `.aof/`, preview with `sync --dry-run`, and apply safely.
   - UI build check for TypeScript/Vite.

## Acceptance Criteria

- Setup UI can view/edit expanded DSL sections as valid config.
- Review/diagnostics include expanded primitive validation issues.
- Existing resource editing remains intact.
- README documents source shape and generated outputs.
- UI still does not execute CLI actions.

## Verification

- `npm run test:unit`
- `npm test`
- `npm run ui:build`
