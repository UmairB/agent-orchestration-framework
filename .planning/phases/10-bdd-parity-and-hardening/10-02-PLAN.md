# Phase 10 Wave 2 Plan: CLI Domain Feature Split And BDD Gap Closure

## Objective

Split the CLI BDD suite into lifecycle, DSL, packages, and adapter-policy domains with full per-feature Node step modules, then close missing CLI-domain BDD coverage gaps identified by the matrix.

## Planning Assumptions

- Wave 1 already provides reusable feature runner, CLI context, and assertion helpers.
- Existing scenario names should be reused unless misleading.
- The old `cli.feature` should be removed or reduced to an intentionally empty/redirecting placeholder only after all scenarios are moved.
- This wave covers CLI-facing BDD; setup UI BDD is handled separately in Wave 3.

## Requirements Covered

- **BDD-01:** Lifecycle scenarios for init, add, sync, validate, doctor, clean, install, catalog, and migration.
- **BDD-02:** DSL render scenarios for resources, MCP, hooks, project docs, settings, runtime overrides, and rules.
- **BDD-03:** Package scenarios for package descriptors, install, lock, dependencies, replay, sync, and conflict behavior.
- **BDD-04:** Adapter warning, JSON payload, strict-mode, and pre-write failure scenarios.

## Tasks

1. Create domain feature files.
   - Move lifecycle scenarios into `test/integration/features/lifecycle.feature`.
   - Move expanded DSL and rendering scenarios into `test/integration/features/dsl.feature`.
   - Move framework package scenarios into `test/integration/features/packages.feature`.
   - Move adapter warning and strict-mode scenarios into `test/integration/features/adapter-policy.feature`.
   - Preserve scenario titles unless a title is misleading after the move.

2. Create full per-domain Node step modules.
   - Add `test/integration/steps/lifecycle.steps.mjs`.
   - Add `test/integration/steps/dsl.steps.mjs`.
   - Add `test/integration/steps/packages.steps.mjs`.
   - Add `test/integration/steps/adapter-policy.steps.mjs`.
   - Each module must export its own step dispatcher for the feature domain.
   - Shared fixtures and assertions should be imported from support modules rather than copied.

3. Wire feature-to-step dispatch.
   - Update the Node runner so each feature file uses its matching step module.
   - Keep feature names and module names easy to infer.
   - Fail clearly if a feature file has no registered step module.
   - Remove the temporary legacy step module when all CLI feature domains have their own modules.

4. Close lifecycle BDD gaps.
   - Ensure happy and error paths exist for `init`, `add`, `sync`, `validate`, `doctor`, and `clean`.
   - Add scenarios for any missing lifecycle command error path identified in `10-BDD-COVERAGE.md`.
   - Keep dry-run and side-effect assertions explicit where relevant.

5. Close DSL BDD gaps.
   - Ensure all v1.1 primitives have user-facing render scenarios across Claude Code and Codex where supported.
   - Add scenarios for missing package descriptor validation only if they are DSL-level config validation rather than package-install behavior.
   - Keep runtime-specific extension/pass-through behavior represented where user-facing.

6. Close package BDD gaps.
   - Add scenarios for npm, git, and file package descriptors being accepted by `validate`.
   - Add lock assertions for package dependency and resolution metadata.
   - Preserve existing installer opt-in and simulated installer scenarios.
   - Preserve pre-write package conflict coverage.

7. Close adapter-policy BDD gaps.
   - Ensure warnings appear in human and JSON diagnostics.
   - Ensure strict-mode failures happen before generated files, lock writes, or installers.
   - Ensure adapter warnings stay out of lock manifests.

8. Update the coverage matrix.
   - Replace moved scenario references with new feature file names.
   - Mark `covered`, `partial`, and `missing` statuses based on the post-split suite.
   - Note any remaining gaps explicitly for Waves 3 or 4.

9. Verify behavior after the split.
   - Run `npm run test:unit`.
   - Run `npm test`.

## Acceptance Criteria

- Domain feature files exist for lifecycle, DSL, packages, and adapter policy.
- Each domain feature has its own Node step module.
- The temporary legacy step module is removed once no feature uses it.
- `npm test` passes with the split feature suite.
- `10-BDD-COVERAGE.md` has exact scenario-level evidence for `BDD-01` through `BDD-04`.

## Verification

- `npm test`
