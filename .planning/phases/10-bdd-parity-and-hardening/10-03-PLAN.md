# Phase 10 Wave 2 Plan: Setup UI API BDD Over HTTP

## Objective

Add BDD-style setup UI API coverage through real HTTP server scenarios for editor save and validation flows without introducing browser E2E.

## Planning Assumptions

- Wave 1 provides the reusable feature runner and assertion support.
- The setup UI BDD scenarios should use `serveSetupUi()` on port `0` and close the server in cleanup.
- Existing `test/setup-ui.test.mjs` is a source of behavior patterns, not a file to delete.
- This wave does not add browser automation or UI component tests.

## Requirements Covered

- **BDD-02:** Adds BDD-style coverage for setup UI editor flows around config primitives and adapter warning payloads.

## Tasks

1. Add setup UI BDD feature file.
   - Create `test/integration/features/setup-ui.feature`.
   - Include scenarios for saving a resource through the setup UI API.
   - Include scenarios for saving expanded sections through the setup UI API.
   - Include scenarios for invalid JSON and route/payload mismatch failures.
   - Include scenarios for adapter warning review payloads after saving warning-producing config.

2. Add setup UI HTTP context helpers.
   - Create `test/integration/support/setup-ui-context.mjs`.
   - Start `serveSetupUi()` with a temp project directory and a test catalog stub.
   - Use port `0` and expose the base URL to steps.
   - Ensure server cleanup runs even when a scenario fails.
   - Remove temp project directories after each scenario.

3. Add setup UI step module.
   - Create `test/integration/steps/setup-ui.steps.mjs`.
   - Implement setup steps for a running setup UI server.
   - Implement HTTP request steps for config resource and section saves.
   - Implement response assertions for status, payload fields, diagnostics, and adapter warnings.
   - Implement filesystem assertions against the temp project `.aof/` config and assets.

4. Wire setup UI feature into the Node runner.
   - Register `setup-ui.feature` with `setup-ui.steps.mjs`.
   - Ensure setup UI scenarios run as part of `npm test`.
   - Keep scenario output consistent with other features.

5. Avoid browser E2E scope creep.
   - Do not use Playwright or browser plugins.
   - Do not add frontend interaction tests.
   - Keep coverage at the HTTP API/editor behavior level.

6. Update the coverage matrix.
   - Add `setup-ui.feature` scenarios as BDD evidence where relevant.
   - Mark any setup UI related coverage as API/editor coverage, not browser E2E.

7. Verify behavior.
   - Run `npm run test:unit`.
   - Run `npm test`.

## Acceptance Criteria

- `setup-ui.feature` exists and runs through the shared Node feature runner.
- Setup UI BDD scenarios exercise real HTTP endpoints from `serveSetupUi()`.
- Server lifecycle is cleaned up reliably after scenarios.
- `npm test` passes with setup UI BDD included.
- No browser E2E tooling is introduced.

## Verification

- `npm run test:unit`
- `npm test`

Write `.planning/phases/10-bdd-parity-and-hardening/10-03-SUMMARY.md` with setup UI scenarios added, HTTP helper shape, matrix updates, tests run, and any API behaviors deferred.
