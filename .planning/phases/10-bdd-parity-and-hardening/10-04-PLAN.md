# Phase 10 Wave 3 Plan: PowerShell BDD Parity And Final Verification

## Objective

Update the PowerShell integration runner to consume the same split feature files with per-domain step modules, document it as a separate required Phase 10 verification command, and close the BDD coverage matrix.

## Planning Assumptions

- Waves 2 and 3 have already produced split feature files and Node step modules.
- PowerShell should consume the same `.feature` files as Node, not a separate scenario copy.
- `npm test` must remain unchanged in scope and should not run PowerShell integration.
- `npm run test:integration:ps` should be the separate required PowerShell verification command.

## Requirements Covered

- **BDD-01:** Confirms lifecycle scenarios run through PowerShell parity.
- **BDD-02:** Confirms DSL and setup UI API scenarios are represented in the shared feature suite.
- **BDD-03:** Confirms package scenarios run through PowerShell parity where supported.
- **BDD-04:** Confirms adapter policy scenarios run through PowerShell parity.

## Tasks

1. Update PowerShell feature discovery.
   - Modify `test/integration/cli.ps1` to discover `test/integration/features/*.feature`.
   - Preserve existing Gherkin-like parsing behavior.
   - Print output using the same `ok - Feature: Scenario` shape.
   - Fail clearly when a feature file has no matching step module.

2. Add Windows-gated skip behavior.
   - Detect non-Windows environments early.
   - Print a clear skip/success message.
   - Exit with status `0` when skipped off Windows.
   - Do not mask failures on Windows.

3. Add per-feature PowerShell step modules.
   - Add `test/integration/steps/lifecycle.steps.ps1`.
   - Add `test/integration/steps/dsl.steps.ps1`.
   - Add `test/integration/steps/packages.steps.ps1`.
   - Add `test/integration/steps/adapter-policy.steps.ps1`.
   - Add `test/integration/steps/setup-ui.steps.ps1`.
   - Share common helpers through `cli.ps1` functions or a small support script if needed.
   - Keep step behavior aligned with the Node modules and shared `.feature` files.

4. Fix package namespace parity in PowerShell fixtures.
   - Ensure any PowerShell package fixture includes `namespace`.
   - Ensure PowerShell JSON assertions can check `packages` metadata as well as legacy `frameworks` metadata.
   - Ensure package conflict and package lock scenarios can run from the shared feature files.

5. Document verification commands.
   - Keep `npm test` behavior unchanged.
   - Ensure `package.json` still exposes `test:integration:ps`.
   - Update README test instructions if they do not clearly mention PowerShell integration as a separate command.
   - Update `10-BDD-COVERAGE.md` to mark PowerShell parity and final statuses.

6. Update planning status documents.
   - Mark `BDD-01` through `BDD-04` complete in `.planning/REQUIREMENTS.md` after verification passes.
   - Update `.planning/ROADMAP.md` Phase 10 status and plan checklist after execution, if this plan is executed as the phase closeout.
   - Update `.planning/STATE.md` to indicate Phase 10 is executed or ready for final milestone closeout, depending on execute-phase conventions.

7. Run final verification.
   - Run `npm run test:unit`.
   - Run `npm test`.
   - Run `npm run test:integration:ps`.
   - If running off Windows, verify the PowerShell command exits successfully with the expected skip message.

## Acceptance Criteria

- PowerShell integration consumes the same split `.feature` files as the Node runner.
- Every feature domain has a corresponding PowerShell step module.
- Off-Windows PowerShell verification skips cleanly with exit code `0`.
- `npm test` is not expanded to include PowerShell integration.
- `npm run test:integration:ps` is documented and passes or skips as expected.
- `10-BDD-COVERAGE.md` marks `BDD-01` through `BDD-04` covered with exact scenario evidence.

## Verification

- `npm run test:unit`
- `npm test`
- `npm run test:integration:ps`
