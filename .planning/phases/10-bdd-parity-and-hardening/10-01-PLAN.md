# Phase 10 Wave 1 Plan: BDD Coverage Matrix And Runner Foundation

## Objective

Create the traceability artifact and shared Node runner foundation needed to split BDD scenarios safely without losing current coverage.

## Planning Assumptions

- `test/integration/cli.feature` remains temporarily valid during this wave so behavior can be preserved before domain splitting.
- The runner foundation should be generic enough for CLI and setup UI scenarios.
- This wave should not add new product behavior.
- The coverage matrix starts with current scenario evidence and known gaps; later waves update it as scenarios move and gaps close.

## Requirements Covered

- **BDD-01:** Starts lifecycle coverage mapping.
- **BDD-02:** Starts DSL coverage mapping.
- **BDD-03:** Starts package coverage mapping.
- **BDD-04:** Starts adapter policy coverage mapping.

## Tasks

1. Create the BDD coverage matrix.
   - Add `.planning/phases/10-bdd-parity-and-hardening/10-BDD-COVERAGE.md`.
   - Include one section per `BDD-01` through `BDD-04`.
   - For each requirement, list exact existing scenario names from `test/integration/cli.feature`.
   - Mark each requirement `covered`, `partial`, or `missing`.
   - Include columns for scenario evidence, gaps, and planned wave.

2. Extract reusable feature parsing and scenario execution utilities.
   - Create `test/integration/support/feature-runner.mjs`.
   - Move feature parsing into a reusable exported function.
   - Add discovery for one or more `.feature` files.
   - Preserve scenario output format: `ok - Feature: Scenario` and `not ok - Feature: Scenario`.
   - Preserve failure aggregation and process exit behavior.

3. Extract shared CLI test context utilities.
   - Create `test/integration/support/cli-context.mjs`.
   - Move temp project/data directory setup, cleanup, CLI execution, environment handling, and command splitting into shared helpers.
   - Preserve `AOF_IN_PROCESS_INTEGRATION=1` behavior for `npm test`.
   - Preserve child-process mode for standalone integration runs.

4. Extract shared assertions.
   - Create `test/integration/support/assertions.mjs`.
   - Move file existence, file content, JSON lock assertions, stdout/stderr assertions, order assertions, and result formatting into reusable helpers.
   - Keep assertion messages at least as useful as current failures.

5. Create a temporary legacy step module.
   - Create `test/integration/steps/cli-legacy.steps.mjs`.
   - Move the current `runStep()` behavior into this module with minimal behavior change.
   - Wire `test/integration/cli.mjs` to use the shared runner and legacy step module against the existing `cli.feature`.
   - Keep this module explicitly temporary; later waves replace it with domain step modules.

6. Verify no behavior changes.
   - Run `npm run test:unit`.
   - Run `npm test`.
   - Update the coverage matrix if the refactor reveals mislabeled or missing scenario evidence.

## Acceptance Criteria

- `npm test` still runs all existing BDD scenarios.
- `test/integration/cli.mjs` uses shared support modules instead of keeping all parsing/context/assertion code inline.
- The coverage matrix exists and maps all four `BDD-*` requirements to exact scenario evidence or gaps.
- No scenarios are lost in this wave.

## Verification

- `npm run test:unit`
- `npm test`

## Completion Artifact

Write `.planning/phases/10-bdd-parity-and-hardening/10-01-SUMMARY.md` with runner modules created, initial coverage matrix status, tests run, and any uncovered BDD gaps carried into later waves.
