# Phase 4 Wave 1 Plan: Config Editor API And File-Backed Persistence

## Goal

Add the server-side foundation for editing `.aof/` configuration from the setup UI: load editable config state, expose central runtime/capability data, validate draft asset saves, and write file-backed asset bodies and enabled runtime overrides without running CLI actions.

## Requirements Covered

- **UI-01:** user can edit `.aof/` configuration through the setup UI.
- **UI-02:** user can create and edit skills, commands, agents, and rules through backend save support.
- **UI-03:** user can configure runtime targets and runtime-specific overrides through backend save support.
- **UI-05:** UI writes valid configuration but does not execute init/apply/install actions.

## Decisions Covered

- **D-09:** runtime targeting is edited as Claude Code / Codex selections.
- **D-10:** runtime-specific overrides exist as per-runtime sections.
- **D-11:** disabled or empty overrides are not written.
- **D-12:** body/instructions overrides are supported.
- **D-17:** explicit Save per asset is the persistence model.
- **D-18:** validation runs before save.
- **D-19:** saving writes config metadata, file-backed body, and override files under `.aof/`.
- **D-20:** UI does not execute CLI actions.

## Implementation Tasks

1. Extract reusable workspace config write helpers.
   - Move or mirror the private `writeWorkspaceConfig()` and `assetBodyPath()` behavior from `src/cli.mjs` into a shared module such as `src/config-editor.mjs` or `src/workspace-config.mjs`.
   - Keep asset body paths based on `RESOURCE_KINDS` and `defaultBodyFile()` from `src/model.mjs`.
   - Preserve existing CLI behavior by updating `src/cli.mjs` to use the shared helper.
   - Ensure packages, project name, top-level runtimes/items, and unrelated resources are preserved when saving one asset.

2. Add editable config loading.
   - Load `.aof/aof.config.json` using `findProjectConfig()` and `loadConfig()`.
   - Return resources with resolved body text and existing override data.
   - Include raw metadata needed by the UI: `id`, `kind`, `name`, `description`, `path`, `paths`, `model`, `tools`, `runtimes`, and override enablement.
   - Return config path and whether the workspace config exists.

3. Add draft asset validation.
   - Validate resource id, kind, runtimes, non-empty runtime selection, and override runtime keys.
   - Reuse central `supportedResourceKinds()` and `supportedRuntimes()`.
   - Validate that overrides cannot change identity fields.
   - Evaluate capability statuses from `CAPABILITIES` and block saves for `unsupported-fail`.
   - Return diagnostics in a UI-friendly shape with severity, path/field, message, and blocking flag.

4. Add setup UI config endpoints.
   - Add `GET /api/config` in `src/setup-ui.mjs`.
   - Add `GET /api/capabilities` in `src/setup-ui.mjs`.
   - Add `PUT /api/config/resources/:kind/:id` or equivalent per-asset save endpoint.
   - Keep endpoint behavior JSON-only and return existing JSON error payloads on failure.
   - Do not add endpoints that run `init`, `apply`, dry-run, or install.

5. Implement file-backed asset save behavior.
   - Create or update `.aof/aof.config.json`.
   - Write body content to `.aof/assets/<plural>/<id>/<BODY_FILE>`.
   - Write enabled runtime override JSON to `.aof/assets/<plural>/<id>/overrides/<runtime>.json`.
   - Omit disabled/empty overrides from config and from override files.
   - Avoid deleting unrelated assets or generated runtime output.

6. Add tests.
   - Unit tests for loading editable config state.
   - Unit tests for saving each kind: skill, command, agent, and rule.
   - Unit tests for runtime target changes.
   - Unit tests for enabled body overrides and omitted disabled overrides.
   - Unit tests proving save validation blocks invalid kind/runtime/id and `unsupported-fail`.
   - Regression tests proving CLI interactive install/config writing still works after helper extraction.

## Acceptance Criteria

- `GET /api/config` returns editable `.aof/` config state with file-backed body content.
- `GET /api/capabilities` exposes central runtime/resource/capability data from `src/model.mjs`.
- A per-asset save endpoint can create and update skills, commands, agents, and rules.
- Saving an asset writes `.aof/aof.config.json`, the asset body file, and enabled override files.
- Disabled or empty overrides are not written.
- Invalid saves are rejected before disk writes where practical.
- No setup UI endpoint runs `init`, `apply`, dry-run, or install.
