# Phase 4 Wave 2 Plan: Asset Workspace UI And Runtime Override Editing

## Goal

Replace the current catalog-only setup screen with an asset workspace UI: kind tabs, asset lists, kind overviews, shared detail editor, inline markdown body editing, runtime checklist, collapsible enabled override sections, and inline capability badges.

## Requirements Covered

- **RTOV-04:** user can see when an asset capability is runtime-specific or unsupported.
- **UI-01:** user can edit `.aof/` configuration through the setup UI.
- **UI-02:** user can create and edit skills, commands, agents, and rules in the UI.
- **UI-03:** user can configure runtime targets and runtime-specific overrides in the UI.
- **UI-04:** UI clearly shows runtime capability differences before config is applied.

## Decisions Covered

- **D-01:** primary UI is an asset workspace.
- **D-02:** workspace organizes assets with Skills, Commands, Agents, and Rules tabs.
- **D-03:** empty selection shows a kind overview.
- **D-05:** one shared detail editor with kind-specific fields.
- **D-06:** inline markdown body editor.
- **D-07:** concise field hints and examples.
- **D-08:** create/edit only; no duplicate or template flow.
- **D-09:** runtime checklist in the asset editor.
- **D-10:** collapsible per-runtime override sections.
- **D-11:** disabled/empty overrides are not written.
- **D-12:** body/instructions overrides are editable.
- **D-13:** inline runtime capability badges.
- **D-14:** mapped capabilities are cautions, not errors.

## Implementation Tasks

1. Restructure the UI app around config editing.
   - Replace the catalog-only `App` flow in `ui/src/main.tsx`.
   - Split into components where useful: `KindTabs`, `AssetList`, `KindOverview`, `AssetEditor`, `RuntimeChecklist`, `OverrideSection`, and `CapabilityBadge`.
   - Keep styling consistent with existing shadcn-style primitives and Tailwind tokens.
   - Keep cards limited to repeated items and editor panels; avoid turning the full page into nested cards.

2. Load config and capability data.
   - Fetch `GET /api/config` on startup.
   - Fetch `GET /api/capabilities` or consume capability data included in config payload.
   - Show loading and error states that fit the work-surface UI.
   - Keep local draft state for the selected asset and save explicitly.

3. Implement kind tabs and asset lists.
   - Add tabs for Skills, Commands, Agents, Rules, and Review.
   - For each kind tab, list assets of that kind with id, description/name, runtime badges, and validation status.
   - Add create-new action for the current kind.
   - Do not add duplicate/copy/template creation.

4. Implement kind overview empty state.
   - Show counts for selected kind.
   - Show runtime coverage for Claude Code and Codex.
   - Show validation status for that kind.
   - Keep the overview operational, not a marketing/landing page.

5. Implement shared asset detail editor.
   - Shared fields: id, name, description, body markdown, runtimes.
   - Kind-specific fields:
     - command: prompt/body wording and command-style hint.
     - agent: instructions/body wording and agent-style hint.
     - rule: paths field and rule guidance hint.
     - skill: description/use-case hint.
   - Add concise field hints and examples.
   - Include inline markdown editing through `Textarea` or a lightweight local editor surface.

6. Implement runtime targeting and overrides.
   - Add Claude Code and Codex runtime checklist.
   - Show per-runtime capability badge next to each runtime.
   - Add collapsible override sections for Claude Code and Codex.
   - Require explicit enablement before an override section contributes save payload data.
   - Support runtime-specific metadata and body/instructions override fields.

7. Implement explicit per-asset save flow.
   - Run local validation before sending save request.
   - Send one asset payload to the Wave 1 save endpoint.
   - Refresh config state after save.
   - Show success/error messages without implying runtime files were applied.

8. Add UI build coverage.
   - Fix TypeScript issues from component extraction.
   - Ensure responsive layout remains usable on narrow viewports.
   - Keep text inside buttons/badges from overflowing.

## Acceptance Criteria

- Setup UI opens directly into an asset workspace, not the old catalog item creator.
- Users can create and edit skills, commands, agents, and rules.
- Users can edit inline markdown body content.
- Users can select Claude Code and/or Codex runtime targets for an asset.
- Users can enable and edit Claude/Codex override sections, including body overrides.
- Capability badges are visible before save/apply.
- Mapped capability behavior is visible as a caution, not an error.
- Explicit Save per asset writes through the Wave 1 API.
- Duplicate/copy/template behavior is absent from Phase 4 UI.
