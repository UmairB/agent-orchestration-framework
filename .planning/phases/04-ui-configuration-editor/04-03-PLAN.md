# Phase 4 Wave 3 Plan: Review Tab, Capability Validation, Docs, And Final Verification

## Goal

Complete the Phase 4 editor with project-wide review, capability summaries, live validation polish, CLI next-command guidance, documentation, and final verification across UI build and CLI/unit behavior.

## Requirements Covered

- **RTOV-04:** user can see runtime-specific or unsupported capabilities.
- **UI-01:** user can edit `.aof/` configuration through the setup UI with validation feedback.
- **UI-04:** UI clearly shows runtime capability differences before config is applied.
- **UI-05:** UI writes valid configuration but does not execute init/apply/install.

## Decisions Covered

- **D-04:** full-project review lives in a dedicated Review tab.
- **D-13:** capability status appears as inline badges.
- **D-14:** mapped capability is a caution, not an error.
- **D-15:** invalid capability states block saves; warnings/cautions remain visible.
- **D-16:** Review tab includes project-wide capability summary.
- **D-18:** validation runs live and as save gate.
- **D-20:** UI shows CLI next commands but does not execute them.

## Implementation Tasks

1. Implement Review tab.
   - Summarize config path and project name.
   - Summarize asset counts by kind.
   - Summarize runtime coverage across Claude Code and Codex.
   - Summarize package intent without exposing install execution controls.
   - Show suggested CLI commands as text, especially `aof apply --dry-run` and relevant `aof install gsd --dry-run` guidance when GSD package intent exists.

2. Add project-wide validation display.
   - Reuse diagnostics from Wave 1 validation/config endpoints.
   - Group validation by severity and field/path.
   - Make blocking save errors distinguishable from warnings/cautions.
   - Ensure validation messages do not claim runtime output has been applied.

3. Add project-wide capability summary.
   - Aggregate statuses across all assets and selected runtimes.
   - Show mapped rule behavior clearly, including Codex rule guidance mapping into `AGENTS.md`.
   - Show unsupported/future statuses as cautions or blockers according to central capability status.
   - Keep the source of truth tied to `src/model.mjs` capability data.

4. Polish live validation and save gates.
   - Ensure the asset editor blocks Save when required fields are invalid.
   - Ensure `unsupported-fail` blocks save.
   - Ensure mapped/future/warning statuses are visible but do not block unless configured as fail.
   - Ensure disabled override sections produce no saved override data.

5. Preserve the execution boundary.
   - Confirm there are no UI controls or API endpoints that run dry-run, apply, init, install, or shell commands.
   - Confirm Review tab presents commands as copyable/readable text only.
   - Keep server-side APIs scoped to config read/write, validation, and capability data.

6. Update docs and help references.
   - Update README setup UI section to describe config editor scope.
   - Document that the UI writes `.aof/` config only and the CLI remains responsible for `aof apply --dry-run`, `aof apply`, and `aof install`.
   - Document supported asset kinds, runtime targets, runtime overrides, and capability warnings.

7. Add final tests.
   - Unit tests for Review/capability aggregation helpers if implemented outside React.
   - UI build verification with `npm run ui:build`.
   - CLI/unit regression with `npm run test:unit` and `npm test`.
   - Add focused BDD or API-level tests if Wave 1 setup UI endpoints can be tested from Node without a browser.

8. Final phase verification.
   - Manually inspect generated `.aof/` files from representative saves.
   - Verify no `.claude/` or `.codex/` runtime output is written by setup UI save paths.
   - Verify Review tab next commands match the CLI boundary.

## Acceptance Criteria

- Review tab shows config validity, runtime/package summary, project-wide capability status, and CLI next commands.
- Mapped capabilities are visible as cautions and invalid capability states block saves.
- UI never executes dry-run, apply, init, install, or shell commands.
- README documents setup UI config editor scope and CLI execution boundary.
- `npm run ui:build`, `npm run test:unit`, and `npm test` pass or any failures are documented with cause.
- Phase 4 requirements RTOV-04 and UI-01 through UI-05 are covered by the three plans.
