# Phase 6 Wave 2 Plan: File-Backed Scaffold Command

## Goal

Add `aof add <kind> <id>` as a script-friendly scaffold command that creates valid file-backed `.aof/` source assets and updates `.aof/aof.config.json` without pushing prompt bodies into inline JSON.

## Requirements Covered

- **CLI-05:** User can scaffold a new `.aof/` primitive from the CLI without hand-editing JSON.

## Decisions Covered

- **D-01:** Phase 6 primary commands include `aof add`.
- **D-09:** `aof add` writes file-backed assets and config entries.
- **D-10:** `aof add` is flag-first and scriptable.
- **D-11:** Collisions fail unless `--force` is passed.
- **D-12:** Phase 6 only needs minimal built-in skeletons for existing v1 kinds.

## Implementation Tasks

1. Add a scaffold helper module.
   - Create `src/scaffold.mjs` or equivalent.
   - Export a function that accepts project directory, kind, id, runtimes, description, force, and optional name.
   - Validate kind via `supportedResourceKinds()` and id via `normalizeId()`.
   - Normalize runtimes using the same supported runtime source as the rest of the CLI.
   - Use `assetBodyPath()` or the same model data to compute `.aof/assets/<plural>/<id>/<BODYFILE>`.

2. Generate minimal built-in skeletons.
   - `skill`: valid `SKILL.md` body with a title and short workflow placeholder.
   - `command`: valid `COMMAND.md` body with a concise command prompt placeholder.
   - `agent`: valid `AGENT.md` body with a role/instructions placeholder.
   - `rule`: valid `RULE.md` body with guidance placeholder and optional paths support if already modeled.
   - Keep templates minimal and deterministic; do not add catalog-backed or named templates.

3. Update `.aof/aof.config.json`.
   - If the workspace config does not exist, create it with `$schema`, `name`, `resources`, and `packages`.
   - Add a resource entry with `kind`, `id`, `description` when provided, `path`, and `runtimes`.
   - Preserve existing config `packages`, `items`, `runtimes`, and unrelated fields where practical.
   - Use file-backed paths with forward slashes.

4. Enforce collision policy.
   - Fail if an existing resource has the same `kind` and normalized `id`.
   - Fail if the target asset file already exists.
   - Error messages must name the conflicting id/path.
   - `--force` may overwrite the scaffolded source file and replace the existing resource metadata for that same kind/id, but must not disturb unrelated resources.

5. Add CLI routing and help.
   - Route `aof add <kind> <id>`.
   - Support `--runtime claude,codex`, `--claude`, `--codex`, `--description`, and `--force`.
   - Missing kind or id should fail with clear usage guidance, not enter an interactive prompt.
   - Add `dryRun` support only if planning finds it cheap and consistent; otherwise defer it explicitly in the summary.

6. Extend BDD coverage.
   - Add scenario for `aof add skill code-review --codex --description "..."`.
   - Assert `.aof/aof.config.json` contains the resource metadata.
   - Assert `.aof/assets/skills/code-review/SKILL.md` exists.
   - Assert `aof add` collision fails with the existing id/path.
   - Assert `--force` replaces the existing same-kind/id scaffold without duplicating resources.
   - Add scenarios for at least one non-skill kind, preferably `rule`, to prove body-file selection is kind-aware.

## Acceptance Criteria

- `aof add <kind> <id>` creates a valid file-backed asset and config entry.
- New prompt/body content is stored in `.aof/assets/...`, not inline JSON.
- Missing required arguments fail with useful messages.
- Unsupported kinds/runtimes fail before file writes.
- Collisions fail by default and are explicit about the conflicting id/path.
- `--force` behavior is deterministic and covered by tests.
