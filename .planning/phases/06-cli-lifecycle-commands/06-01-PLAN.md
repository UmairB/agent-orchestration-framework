# Phase 6 Wave 1 Plan: Top-Level Diagnostics And Lifecycle Help

## Goal

Promote source validation and project-health diagnostics to the top-level lifecycle CLI surface while preserving the existing diagnostic logic and making help output lifecycle-first.

## Requirements Covered

- **CLI-07:** User can validate `.aof/` configuration and DSL source files with machine-readable diagnostics.
- **CLI-08:** User can diagnose project setup issues including stale lock state, package drift, missing assistant support, and unwritable outputs.

## Decisions Covered

- **D-01:** Phase 6 primary commands include `aof validate` and `aof doctor`.
- **D-03:** `aof validate` and `aof doctor` are top-level primary commands.
- **D-04:** Help output should be lifecycle-first.
- **D-17:** `validate` checks source only.
- **D-18:** `doctor` checks project health beyond validation.
- **D-19:** Errors fail, warnings pass by default; `--strict` can promote warnings.
- **D-20:** Human-readable output by default and `--json` for automation.

## Implementation Tasks

1. Add top-level command routing.
   - Route `aof validate` to the existing validation flow.
   - Route `aof doctor` to the existing doctor flow.
   - Keep the command implementation small by delegating to shared helpers instead of duplicating the current `configCommand()` internals.
   - Leave `aof config show` available as a supporting inspection command.

2. Add strict warning handling.
   - Extend validation/doctor command output handling so `--strict` treats warning diagnostics/checks as failures.
   - Preserve current default behavior: errors exit non-zero, warnings exit zero.
   - Add `strict` to the boolean flag list in `parseOptions()`.
   - Ensure JSON output includes enough status metadata for automation to distinguish valid/healthy/strict failures.

3. Keep validation and doctor responsibilities split.
   - `aof validate` reports config/source diagnostics from `validateConfig()`.
   - `aof doctor` reports broader health from `doctorConfig()`.
   - Do not add generated-output drift or environment checks to `validate`.

4. Reorganize help text.
   - Present lifecycle commands first: `init`, `add`, `apply`, `sync`, `validate`, `doctor`, `clean`.
   - Present supporting commands after: `install`, `catalog`, `config`.
   - Include `--json` and `--strict` where relevant.
   - Do not add a full `aof help <command>` system in this phase.

5. Extend BDD coverage.
   - Add scenarios for `aof validate` human and JSON output.
   - Add scenarios for `aof validate --strict` warning promotion if a warning-only fixture exists or can be created cleanly.
   - Add scenarios for `aof doctor` human and JSON output.
   - Add help-output assertions showing lifecycle-first commands.
   - Reuse existing invalid `.aof` and stale legacy config fixtures where possible.

6. Add or adjust focused unit tests if needed.
   - Prefer unit coverage for strict status calculation if it is extracted from `src/cli.mjs`.
   - Keep broad command behavior in BDD tests.

## Acceptance Criteria

- `aof validate` works as the primary validation command.
- `aof doctor` works as the primary project-health command.
- Both commands support human-readable defaults and `--json`.
- Errors exit non-zero; warnings pass unless `--strict` is passed.
- Help output shows the lifecycle commands prominently.
- Existing `aof config show` behavior remains intact.
