# Phase 8 Wave 2 Plan: CLI Warning Output And Strict Gates

## Objective

Surface shared adapter warnings through `validate`, `doctor`, `apply`, and `sync`, and make `--strict` fail before side effects whenever adapter warnings are present.

## Planning Assumptions

- Human-readable output remains the default.
- JSON output must preserve existing fields and add top-level `adapterWarnings`.
- `apply --strict` and `sync --strict` are pre-write gates.
- `--force` remains limited to generated-output drift and does not bypass adapter strict failures.

## Requirements Covered

- **ADPT-01:** CLI commands show skipped/unsupported runtime warnings.
- **ADPT-02:** CLI commands show lossy mapping warnings.
- **ADPT-04:** `--strict` promotes adapter warnings to command failures for CI.

## Tasks

1. Add adapter warnings to config inspection.
   - Update `validateConfig()` usage or add a companion helper that loads normalized config only when validation has no errors.
   - Update `inspectConfig()` to include `adapterWarnings`.
   - Update `doctorConfig()` to include `adapterWarnings`.
   - Add a `doctor` check such as `adapter-degradation` with `warning` severity when adapter warnings exist and `ok` when none exist.
   - Keep adapter warnings out of regular `diagnostics` so structural validation and adapter policy remain distinguishable.

2. Add CLI warning formatting.
   - Add a compact `adapter-warnings:` human block in `src/cli.mjs`.
   - Print it before apply/sync action output.
   - Print it for validate/doctor even when there are no structural validation errors.
   - Include code, config path, runtime, source primitive, generated path when known, reason, and remediation.
   - Keep output deterministic by sorting warnings by path, runtime, code, then id.

3. Add JSON output.
   - Add top-level `adapterWarnings` to `validate --json`.
   - Add top-level `adapterWarnings` to `doctor --json`.
   - Add JSON dry-run output for `apply --dry-run --json` if not already present.
   - Add JSON dry-run output for `sync --dry-run --json` if not already present.
   - Ensure dry-run JSON includes actions, lock preview, and adapter warnings without writing files or lock state.

4. Enforce strict mode consistently.
   - Make `validate --strict` fail when adapter warnings exist.
   - Make `doctor --strict` fail when adapter warnings exist.
   - Make `apply --strict` fail before `executeApplyActions()` and before `writeLock()`.
   - Make `sync --strict` fail before file actions, lock writes, and framework installers.
   - Ensure `apply --strict --force` and `sync --strict --force` still fail on adapter warnings.
   - Use a clear error message that names adapter warnings as the strict-mode reason.

5. Update help text.
   - Add `--strict` to `aof apply` and `aof sync` usage.
   - Mention that `--strict` promotes adapter warnings to failures.
   - Keep existing command synopsis compact.

6. Add integration and config-inspect tests.
   - Unit tests: `inspectConfig()` and `doctorConfig()` expose `adapterWarnings`.
   - BDD: `validate --json` includes `adapterWarnings`.
   - BDD: `doctor --strict` fails on adapter warnings.
   - BDD: `apply --dry-run` prints `adapter-warnings:` before `create:`.
   - BDD: `sync --dry-run` prints `adapter-warnings:` before `create:`.
   - BDD: `apply --strict` fails and leaves generated files and lock state absent.
   - BDD: `sync --strict --force` fails and leaves generated files, lock state, and install attempts absent.

## Acceptance Criteria

- `validate`, `doctor`, `apply`, and `sync` all surface adapter warnings from the same warning objects.
- Human warning blocks are compact, deterministic, and actionable.
- JSON output includes top-level `adapterWarnings` where automation uses it.
- Strict mode fails all four commands when adapter warnings exist.
- Strict apply/sync failures occur before writes, deletes, lock updates, or installers.
