# Phase 8 Wave 1 Plan: Shared Adapter Warning Model

## Objective

Add a single command-time adapter warning model that can explain unsupported, skipped, and lossy runtime behavior without changing lock state or duplicating warning logic across commands.

## Planning Assumptions

- Adapter warnings are not structural config validation errors. They are computed only after the config is valid enough to normalize.
- Warning collection is pure and side-effect-free.
- Existing Codex rule rendering to `AGENTS.md` is intentional mapped output and must not become warning noise.
- Runtime-namespaced extension objects are matching-runtime pass-throughs and non-matching-runtime silent ignores.

## Requirements Covered

- **ADPT-01:** Defines skipped/unsupported runtime warnings.
- **ADPT-02:** Defines lossy runtime mapping warnings.
- **ADPT-03:** Preserves runtime-namespaced extension pass-through semantics.
- **ADPT-04:** Provides the shared warning data that strict mode will promote to failures in later waves.

## Tasks

1. Add shared adapter warning constants and object shape.
   - Create `src/adapter-warnings.mjs`.
   - Export warning code constants for unsupported feature, skipped runtime output, and lossy runtime mapping.
   - Export a single warning factory or normalizer that always returns:
     - `code`
     - `severity`
     - `path`
     - `kind`
     - `id`
     - `runtime`
     - `generatedPath`
     - `reason`
     - `remediation`
   - Keep `severity` as `"warning"` for Phase 8 adapter warnings.

2. Add a shared analyzer entry point.
   - Implement `collectAdapterWarnings(config, options)`.
   - Accept requested runtimes, target directory, and global/local context.
   - Use the normalized config shape: `resources`, `mcpServers`, `hooks`, `projectDocs`, and `settings`.
   - Return `[]` for unsupported warning analysis when structural data is absent or already filtered out by requested runtimes.

3. Model runtime degradation capabilities.
   - Add small policy helpers in `src/adapter-warnings.mjs` or constants in `src/model.mjs` if they are generally useful.
   - Classify runtime-specific extension objects as matching-runtime pass-throughs, not warnings.
   - Classify current rule-to-Codex `AGENTS.md` output as intentional supported mapping, not a Phase 8 warning.
   - Classify unsupported future primitive/runtime combinations as warning-and-skip by default.
   - Classify vendor-neutral settings that cannot be directly represented by a requested runtime as adapter warnings unless a safe mapping already exists.

4. Include generated paths where known.
   - Use deterministic output path helpers or duplicated path policy only where stable.
   - Provide `generatedPath` for runtime config targets such as `.mcp.json`, `.claude/settings.json`, `.codex/config.toml`, `AGENTS.md`, and `CLAUDE.md`.
   - Leave `generatedPath` null only when no target path can be known before rendering.

5. Add focused unit tests.
   - Add `test/adapter-warnings.test.mjs`.
   - Cover warning object shape and code stability.
   - Cover unsupported/skipped warnings.
   - Cover lossy warning behavior for a policy-defined lossy feature.
   - Cover silent non-matching runtime extension objects.
   - Cover no warning for intentional Codex rule guidance mapping.
   - Cover top-level adapter warnings are not written into lock manifests.
   - Register the test in `scripts/test-unit.mjs` and `scripts/test.mjs`.

## Acceptance Criteria

- A single exported analyzer returns adapter warnings in the agreed shape.
- Warning data is stable enough for CLI JSON output and UI review payloads.
- Runtime-specific extension objects do not emit warnings for non-matching runtimes.
- Existing Codex rule mapping does not emit an adapter warning.
- Unit coverage proves warning collection is pure and side-effect-free.
