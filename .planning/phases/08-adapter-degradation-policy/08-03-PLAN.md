# Phase 8 Wave 3 Plan: Review Surfaces And Policy Documentation

## Objective

Expose adapter warnings in non-executing review surfaces and document the degradation policy so users can understand warnings before running CLI writes.

## Planning Assumptions

- Setup UI remains a configuration editor and review surface only.
- CLI remains responsible for `apply`, `sync`, `install`, and other side effects.
- The UI should consume the same adapter warning objects as CLI JSON output rather than inventing a separate warning shape.

## Requirements Covered

- **ADPT-01:** Review surfaces show unsupported/skipped runtime warnings.
- **ADPT-02:** Review surfaces show lossy mapping warnings.
- **ADPT-03:** Docs and tests clarify runtime-namespaced extension pass-through.
- **ADPT-04:** Docs explain strict mode for CI.

## Tasks

1. Add adapter warnings to editable config payloads.
   - Update `src/config-editor.mjs` so `loadEditableConfig()` includes `adapterWarnings`.
   - Reuse `collectAdapterWarnings()` after validation succeeds.
   - Return an empty array when the config is missing or structurally invalid.
   - Keep existing `diagnostics` and `capabilities` fields unchanged.

2. Surface warnings through setup UI API.
   - Update `src/setup-ui.mjs` only if the existing config endpoint needs response shaping.
   - Ensure saved section responses return refreshed `adapterWarnings`.
   - Preserve payload size limits, route validation, JSON parse validation, and path safety.

3. Render warnings in the setup UI review surface.
   - Update `ui/src/main.tsx` to display adapter warnings in the Review area.
   - Use compact rows that include code, runtime, source primitive, generated path, reason, and remediation.
   - Keep warning styling distinct from blocking validation errors.
   - Do not add buttons that execute CLI commands.

4. Update public documentation.
   - Update `README.md` with:
     - what adapter warnings mean
     - which commands show them
     - how `--strict` behaves
     - why `--force` does not bypass strict adapter warnings
     - how runtime-specific extension objects pass only to matching runtimes
     - examples of human and JSON warning output

5. Add API/UI tests.
   - Unit test `loadEditableConfig()` includes adapter warnings.
   - Unit/API test save responses include refreshed adapter warnings where applicable.
   - Setup UI test confirms warning payload shape is served.
   - UI build confirms the Review rendering compiles.

## Acceptance Criteria

- Setup UI review data includes adapter warnings without adding execution behavior.
- Runtime-specific extension objects remain silent for non-matching runtimes in UI/review output.
- README documents the adapter degradation policy and strict mode clearly.
- UI and setup API tests cover the warning payload shape.

- `npm run test:unit`
- `npm run ui:build`
- `npm test`
