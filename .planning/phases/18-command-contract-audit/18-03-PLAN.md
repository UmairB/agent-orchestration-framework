# Phase 18 Wave 3 Plan: Help, Errors, And BDD Contract

## Objective

Define the user-facing help, output, error, dry-run, and BDD expectations for the namespaced CLI rewrite so later implementation can be verified consistently.

## Planning Assumptions

- This wave does not update runtime code or README.
- It produces the test contract that Phases 19-22 must satisfy.
- Helpful failures for removed commands are allowed, but removed commands must not execute or alias.

## Requirements Covered

- **CLI-01:** Complete documented command contract.
- **CLI-02:** Command names match side effects.
- **CLI-03:** No legacy aliases.
- **CLI-04:** Help output grouped by product area and examples.

## Decisions Covered

- **D-29..D-37:** Removed command behavior, help, success output, error output, and dry-run output.

## Tasks

1. Define help layout.
   - Add a Help Contract section to `18-CLI-CONTRACT.md`.
   - Group help by product area: Project setup, Assets, Packages, Project diagnostics.
   - Include common workflow examples, not only syntax.

2. Define success output patterns.
   - For write commands, require output that says which source files changed.
   - For render/apply commands, require output that says which runtimes were targeted.
   - For package install commands, require explicit network/package-code boundary output.
   - For UI launch, require output that says a local editor is running, the URL, project path, and how to stop it.

3. Define error output patterns.
   - Unknown removed commands should name the invalid command and point to the new namespace.
   - Missing required arguments should explain the argument and show a concrete example.
   - Partial commands that support prompting should prompt in interactive terminals and fail clearly in non-TTY automation.
   - Catalog commands should not initialize SQLite or create catalog state.

4. Define dry-run patterns.
   - Dry-run must explicitly state that no writes happen.
   - Package dry-runs must explicitly state that no networked installer commands run.
   - Dry-run output should list affected files or commands.

5. Create `.planning/phases/18-command-contract-audit/18-BDD-CONTRACT.md`.
   - List BDD scenarios required for Phases 19-22.
   - Include accepted namespaced commands.
   - Include rejected legacy commands.
   - Include missing-argument interactive behavior.
   - Include no SQLite/catalog side effects.
   - Include PowerShell parity expectations for CLI-facing behavior.

6. Verify decision coverage.
   - Ensure D-29 through D-37 appear in either `18-CLI-CONTRACT.md` or `18-BDD-CONTRACT.md`.
   - Ensure CLI-01 through CLI-04 are covered by the artifacts.

## Acceptance Criteria

- `18-CLI-CONTRACT.md` contains a Help Contract section.
- `18-BDD-CONTRACT.md` lists concrete scenarios for accepted and removed commands.
- Removed commands are specified as non-executing failures, not aliases.
- Dry-run and package network-boundary expectations are explicit.
- Later implementation phases can use the BDD contract without re-discussing CLI semantics.
