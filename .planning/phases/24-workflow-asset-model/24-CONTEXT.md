# Phase 24: Workflow Asset Model - Context

**Gathered:** 2026-05-12
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 24 adds first-class optional workflow assets to AOF. A workflow is a shared process body that can be rendered into Claude and Codex generated output and referenced by runtime-specific wrappers.

This phase should implement the model, validation, rendering, and global/project behavior needed for workflow-backed wrappers. It should not force existing simple skills, commands, agents, or rules to use workflows. Simple assets remain direct-render assets with no argument support, as locked in Phase 23.

The primary product shape is: users define a shared workflow once, then attach Claude command wrappers and Codex skill wrappers to that workflow. The wrappers may be generated by default or explicitly authored when Claude and Codex need different runtime-facing wording.

</domain>

<decisions>
## Implementation Decisions

### Workflow Declaration
- **D-01:** AOF config should add a top-level `workflows` section, rather than modeling workflows as ordinary `resources`.
- **D-02:** Workflow source files should live at `.aof/assets/workflows/<id>/WORKFLOW.md`.
- **D-03:** Workflows are shared process bodies, not directly invoked assistant commands or skills. Runtime wrappers remain the user-facing command/skill entry points.
- **D-04:** Project-local workflows and global workflows are both in scope for Phase 24.
- **D-05:** Global workflows should participate in project `globalRefs`, source scope tracking, validation, rendering, and lock traceability the same way referenced global assets do.

### Runtime Rendering
- **D-06:** Generated workflow files should be written under an AOF-owned runtime namespace:
  - `.claude/aof/workflows/<id>.md`
  - `.codex/aof/workflows/<id>.md`
- **D-07:** AOF should not write generated workflows to bare `.claude/workflows` or `.codex/workflows` paths because neither runtime has a native workflow primitive. The `aof/` namespace makes ownership explicit.
- **D-08:** Workflow `runtimes` should control which runtime workflow files are generated.

### Wrapper Binding
- **D-09:** Runtime wrapper assets bind to a workflow with `workflow: "<id>"`.
- **D-10:** The `workflow` property should be the source of truth for wrapper-to-workflow binding. Content placeholders may exist later, but should not be the primary relationship model.
- **D-11:** Wrapper bodies use a hybrid model: explicit body wins; if no body is provided, AOF generates a default runtime wrapper body.
- **D-12:** Generated default wrapper bodies should contain the resolved runtime workflow path directly, not unresolved template syntax.
- **D-13:** Claude command wrappers and Codex skill wrappers can reference the same workflow, but remain separate assets because their runtime-facing shape can differ significantly.

### Workflow-Backed Arguments
- **D-14:** Workflow-backed arguments should be declared on the workflow as shared logical inputs.
- **D-15:** Wrapper assets may override runtime-facing argument presentation.
- **D-16:** Phase 24 should support both `argumentHint` for a freeform argument string and simple named argument metadata such as `{ name, description, required }`.
- **D-17:** Argument metadata is documentation/rendering metadata only. AOF does not parse, validate user invocation text, or execute arguments.
- **D-18:** Simple assets still reject argument fields and argument-looking markers unless they are explicitly workflow-backed through `workflow`.

### Validation Contract
- **D-19:** Validation should fail when a wrapper's `workflow` does not reference an existing project or referenced global workflow.
- **D-20:** Validation should fail when a wrapper targets a runtime that its workflow does not target.
- **D-21:** Validation should fail when wrapper argument overrides reference arguments that are not declared by the workflow.
- **D-22:** Validation diagnostics should distinguish missing workflow, runtime mismatch, and invalid argument override cases.

### the agent's Discretion
- Choose exact config field names for named argument metadata if they remain simple and readable.
- Choose exact generated default wrapper wording if it includes the resolved workflow path and runtime-appropriate argument guidance.
- Choose the internal implementation split between existing resource validation/rendering modules and new workflow-specific helpers, as long as project and global workflows share one contract.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `src/model.mjs` owns resource kinds, body filenames, capability status, and runtime metadata. Phase 24 likely needs workflow model additions here or a parallel exported workflow definition.
- `src/config-inspect.mjs` owns project/global validation and now contains the Phase 23 simple-argument and unsupported-capability checks. Workflow validation should integrate here.
- `src/dsl.mjs` resolves file-backed resources and associated files. Workflow source resolution should follow the same path discipline and global/project source behavior.
- `src/adapters.mjs` owns runtime output planning. It already renders main resources plus associated files and can be extended or paired with workflow output rendering.
- `src/render-plan.mjs` and `src/lock.mjs` already support lock-owned generated files with source metadata. Workflow generated files should use the same drift and cleanup machinery.
- `src/config-editor.mjs` and `src/setup-ui.mjs` expose setup UI config APIs. Phase 24 should keep UI changes minimal unless needed to preserve valid config editing; fuller mode controls belong to Phase 26.

### Established Patterns
- File-backed assets live under `.aof/assets/<plural>/<id>/<BODY>.md`; workflows should mirror this with `.aof/assets/workflows/<id>/WORKFLOW.md`.
- Runtime output files are generated under `.claude/` and `.codex/`, tracked in `.aof/aof.lock.json`, and protected from drifted overwrites.
- Referenced global assets are validated only when referenced by a project and retain source scope in diagnostics and lock metadata.
- BDD coverage is expected for new user-visible CLI behavior, with PowerShell parity when CLI scenarios change.

### Integration Points
- Config schema and model parsing need to recognize top-level `workflows`.
- Project and global validation need to resolve workflow IDs across local workflows and `globalRefs`.
- Apply/render flow needs to include workflow outputs before or alongside wrapper outputs so generated wrappers can reference resolved runtime workflow paths.
- Wrapper rendering needs access to the resolved workflow runtime path and argument metadata when generating default bodies.
- Setup UI API validation must reject invalid workflow-backed wrapper config even before the full Phase 26 authoring UI exists.

</code_context>

<specifics>
## Specific Ideas

### Example workflow source shape

```json
{
  "workflows": [
    {
      "id": "audit-milestone",
      "description": "Audit milestone completion",
      "path": "assets/workflows/audit-milestone/WORKFLOW.md",
      "runtimes": ["claude", "codex"],
      "argumentHint": "<milestone>",
      "arguments": [
        { "name": "milestone", "description": "Milestone version or phase range", "required": true }
      ]
    }
  ]
}
```

### Example Claude command wrapper

```json
{
  "kind": "command",
  "id": "gsd/audit-milestone",
  "runtimes": ["claude"],
  "workflow": "audit-milestone",
  "argumentOverrides": {
    "milestone": {
      "description": "Milestone to audit from Claude command arguments"
    }
  }
}
```

Expected generated workflow path:

```text
.claude/aof/workflows/audit-milestone.md
```

Expected generated default command body should reference that resolved path directly.

### Example Codex skill wrapper

```json
{
  "kind": "skill",
  "id": "gsd-audit-milestone",
  "runtimes": ["codex"],
  "workflow": "audit-milestone"
}
```

Expected generated workflow path:

```text
.codex/aof/workflows/audit-milestone.md
```

Expected generated default skill body should reference that resolved path directly and include runtime-appropriate argument guidance.

</specifics>
