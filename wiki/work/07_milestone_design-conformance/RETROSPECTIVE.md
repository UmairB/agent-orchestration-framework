# 07 · Design-Conformance Verification — Retrospective

Distilled lessons from how execution actually went. One `R<n>` per lesson; append-only, never renumber.
Clean catches with no process lesson are not entries — they live in VERIFICATION/STATE. This milestone
had **no blocker stops** and one VERIFICATION finding (F1, a resolved local-install drift with no carried
lesson). R1–R3 are the three carried `## Feedback (for retro)` notes (now archived at the close); R4 is
the cross-session acceptance friction this milestone's machinery-only shape exposed.

## R1 — Enforce a derived artifact's freshness as a boundary, not a developer habit

- **Kind:** near-miss · **Area:** process · **Stage:** build · **Owner:** developer · **Raised by:** aof-architect (review)
- **What happened:** the derived `src/bundle/manifest.json` must be regenerated by
  `scripts/generate-bundle-manifest.mjs` after every bundle-body edit; ADR-005 leaves this as a developer
  habit caught only by `acd-bundle-manifest-hashes` going RED. It was handled correctly this build
  (regenerated before the suite ran), but a stale derived artifact is easy to ship by forgetting the step.
- **Why:** a derived/generated artifact whose freshness depends on a remembered manual step will eventually
  be committed stale — the guard catches it *after* the fact (a red suite), not *before* the commit.
- **Lesson:** make a derived artifact's freshness an enforced boundary — a generator `--check` mode wired
  into the test run that fails loudly (or auto-regenerates) so a stale manifest cannot be committed —
  rather than a habit a red arch-test eventually catches. Applies to any future generated-from-source asset.
- **Refs:** STATE `## Feedback (for retro)`; ADR-005/006; `scripts/generate-bundle-manifest.mjs`,
  `acd-bundle-manifest-hashes`.

## R2 — Plan the parallel-build / serial-integrate shape up front when stories share test files, a runner, or a derived artifact

- **Kind:** near-miss · **Area:** process · **Stage:** build · **Owner:** orchestrator · **Raised by:** orchestrator (build)
- **What happened:** ADR-006 framed the three stories as independent "by construction" on disjoint
  *production* files, but three of the six fitness functions read assets owned by >1 story
  (`acd-design-role-split`, `acd-conformance-verdict-contract`, `acd-design-conformance-bundled`), and
  `scripts/test.mjs` + the manifest are co-touched — so the *test* layer is genuinely serial-integrate.
  The two-wave build (parallel bundle content → one integrator for the cross-cutting tests + wiring +
  manifest) handled it cleanly.
- **Why:** "independent by construction" held for the production files but not the test layer; the coupling
  lived in the cross-cutting arch-tests + the shared runner/manifest, which a pure story fan-out doesn't
  account for.
- **Lesson:** when stories share test files, a test runner, or a derived artifact, plan a
  parallel-build / serial-integrate shape with an explicit integrator wave **up front**, rather than
  discovering the coupling mid-fan-out. Future UI/bundle milestones should expect this shape.
- **Refs:** STATE `## Feedback (for retro)`; ADR-006; the two-wave build (STATE Progress).

## R3 — Isolate an adversarial fitness-function reviewer (worktree or in-memory) so its mutations don't spook concurrent reviewers

- **Kind:** near-miss · **Area:** process · **Stage:** verify · **Owner:** architect · **Raised by:** orchestrator (review)
- **What happened:** the structural reviewer mutated bundled assets in-place to prove the guards trip,
  while other reviewers ran concurrently — producing a spurious "suite RED / manifest stale" reading that
  a revert + independent re-run cleared (no shipped defect).
- **Why:** an adversarial reviewer that mutates the shared working tree to prove a guard bites will corrupt
  any concurrent reader's view of that tree.
- **Lesson:** worktree-isolate an adversarial reviewer (or have it mutate in-memory copies, as the
  drift-guard's own self-test does) so its deliberate breakage never reads as a real failure to a
  concurrent reviewer.
- **Refs:** STATE `## Feedback (for retro)`; the drift-guard self-test (`acd-design-conformance-bundled`).

## R4 — An enabler/machinery milestone must not gate its own acceptance on scenarios only a downstream consumer can exercise

- **Kind:** misunderstanding · **Area:** process · **Stage:** verify · **Owner:** product-owner · **Raised by:** orchestrator (verify, cross-session)
- **What happened:** 07 delivers the design-conformance **loop** (agents, commands, template, schema,
  fitness functions) but owns no served UI surface of its own. Its acceptance criteria nonetheless
  included 5 `@uat` + 22 `@manual` scenarios that need a served app + a committed baseline + a real render
  — exercisable only on a downstream UI consumer. With no such consumer among 08–12 (all non-UI), those
  residuals stayed un-runnable, acceptance was **HELD across two sessions**, and a green, blocker-free
  milestone sat parked `in-progress`, blocking `aof work next`. It was finally accepted on the structural
  deliverable, with the residuals carried forward to the first real UI consumer.
- **Why:** consumer-dependent scenarios (the loop's *output quality* on a real surface) were homed on the
  *enabler* milestone instead of on the consumer that can actually run them — so the enabler could never
  be fully accepted on its own.
- **Lesson:** when a milestone builds verification machinery (or any enabler) whose output-quality can
  only be tested on a future consumer, gate the enabler's acceptance on its **structural deliverable**,
  and home the consumer-dependent `@uat`/served-app scenarios on that consumer — a **UAT session**
  (`aof:add-uat`) or the consumer milestone's own verify — flagged "exercise on first consumer," not
  "blocks this milestone." Decide this at refine, so the enabler isn't born un-acceptable.
- **Refs:** VERIFICATION `## Accept decision` (accepted on machinery; residuals carried forward);
  SPEC `## Scope` (the `toHaveScreenshot` *seam* is in scope, building baselines is a QA follow-on).
