# 10 · Graphify Memory Backend — Research

**Gathered:** 2026-06-21
**Method:** The graphify facts gathered in 09's RESEARCH.md (Findings A–I, A1–A8) are treated as KNOWN and cited as `09-RESEARCH §X` — NOT re-derived. New upstream research was done ONLY for the two questions 09 did not cover: what graphify extracts from `.md`/prose, and node-provenance granularity. New sources: graphify `docs/how-it-works.md` (fetched via `gh api`, the `v8`/`main` tree), the `docs/node-summaries-rfc.md` RFC, and upstream issues #1122 (code-only `extract` gates on an LLM key) and #1178 (`source_location` is a bare line number with no file qualifier). The frozen aof contracts were read from the real code: `src/graphify.mjs`, `src/commands/graph-build.mjs`, `src/commands/graph-query.mjs`, `src/command-core.mjs`, `src/work-memory.mjs`, `src/memory/local-indexing.mjs` / `local-retrieval.mjs` / `local-backend.mjs` / `none-backend.mjs`, and the 05/09 ARCHITECTURE.md ADRs.
**Status:** No live graphify binary was installed — every claim about graphify's runtime behaviour is desk research from upstream docs/issues and is flagged where it must be confirmed live (`@manual`). The aof-side contracts (the seams a backend calls) are confirmed against the real code at the cited `file:line`.

## A. Markdown/prose is extracted ONLY by the LLM pass — there is NO offline path that yields prose nodes (decisive for Q1)

- **Finding:** graphify runs three passes (`how-it-works.md`): **Pass 1 — code (tree-sitter AST, "free, no API calls"); Pass 2 — video/audio (faster-whisper, local); Pass 3 — "Docs, papers, images (Claude subagents, costs tokens)".** Markdown is a Pass-3 input, NOT Pass 1 — verbatim: *"Claude runs in parallel over markdown, PDFs, images, and transcripts. Each subagent reads a batch of files and outputs a JSON fragment: nodes, edges…"*. The doc is explicit that **"If a corpus contains only code files, Pass 3 is skipped entirely; semantic extraction is reserved for docs, papers, images, and transcripts."** The aof work stream (`wiki/work/**`) is a corpus of `.md` files (markdown is NOT among the ~36 tree-sitter grammars, `09-RESEARCH §E`) — so over the work stream Pass 1 produces ~nothing and **Pass 3 (the LLM hop) is the ONLY producer of nodes.** The code-only escape hatch from issue #1122 (`graphify update <path> --no-cluster`, which runs "no LLM needed") only re-extracts CODE via AST; on a markdown-only corpus it skips Pass 3 and yields no meaningful graph.
- **Constraint:** **A graph built over the work stream's `.md` is INHERENTLY an egress event** — building it sends the retrospectives/ADRs to the configured LLM backend (`09-RESEARCH §F`; in aof's terms `graph:build`'s `egress: "docs-media"`, never `"none"`). There is NO `egress: none` / `backend: null` build that produces useful prose nodes. The "code-only/offline path" hoped for in Q1 does not exist for prose. Building a *memory graph of your own work stream therefore egresses the entire work stream to a third-party LLM* unless the backend is the local `ollama` (`09-RESEARCH §F`; aof still classifies ollama as `egress: "docs-media"` because the hop ran — `src/commands/graph-build.mjs:42-49`). This collides directly with 05/ADR-001's premise that memory is a cheap derived index of files aof already holds locally.
- **Source:** `docs/how-it-works.md` (Pass 1/2/3, "If a corpus contains only code files, Pass 3 is skipped entirely") — github.com/safishamsi/graphify, fetched via `gh api .../contents/docs/how-it-works.md`; issue https://github.com/safishamsi/graphify/issues/1122 ; `09-RESEARCH §E/§F`.

## B. extract REQUIRES an LLM key — even structurally; the code-only path is a different verb (reinforces A)

- **Finding:** Issue #1122 (open): `graphify extract <path>` **"refuses to run … unless an LLM API key is set"** because it `detect_backend()`s and exits `no LLM API key found` **BEFORE** detecting corpus composition — *even for a code-only corpus that needs no model*. The AST-only path is reached via a **different verb**: `graphify update <path> --no-cluster` ("no LLM needed → graph.json written"). aof's driver hardwires the build to `extract` (`graphifyBuildArgs` → `["extract", input.path, "--out", projectRoot, …]`, `src/graphify.mjs:113-122`) and only adds `--backend` when `input.backend` is set (so a null backend passes NO `--backend` — `src/commands/graph-build.mjs` `classifyEgress`).
- **Constraint:** With graphify 0.8.44 (the pinned version, `src/graphify.mjs:45`) and the `extract` verb aof drives, **a `backend:null` / offline build of the work stream will FAIL at the `detect_backend()` gate** (no key), not silently produce an empty graph — and even if it ran, Pass 3 is where prose nodes come from (Finding A), so a keyless build cannot index the work stream. The architect must reckon that the aof `graph:build` egress=`none` path (`src/commands/graph-build.mjs:47`) is, for a markdown corpus, **not a build-the-work-stream path at all** — it is a code-only path. (Whether 0.8.44 specifically still gates `extract` on a key, and whether `update --no-cluster` is exposed/stable, is live-only — assumption B1/B2.)
- **Source:** issue https://github.com/safishamsi/graphify/issues/1122 ; `src/graphify.mjs:113-147`; `src/commands/graph-build.mjs:36-49`.

## C. graph.json nodes carry FILE-LEVEL provenance only — `source_file`, NO line/section/anchor (decisive for Q2)

- **Finding:** The canonical node schema in `how-it-works.md` is exactly **`id` / `label` / `file_type` (`code`|`document`|`paper`|`image`|`rationale`) / `source_file` ("where it came from")** — there is **NO `line`, `source_location`, anchor, or section field in the documented node shape** (`09-RESEARCH §D` lists the same: `file_type`/`source_file`/`community`/`norm_label`, no line). aof's normalizer mirrors this precisely: `normalizeNode` maps `id/label/file_type/source_file/community/norm_label` and carries **no line/section field** (`src/graphify.mjs:253-262`). A separate, code-only `source_location` DOES exist on some AST nodes — but issue #1178 documents it as a **bare line number ("L11", "L33", "L207") with NO file qualifier**, and it is a code-symbol field (the issue is about TS/React AST symbols), not part of the canonical node schema and absent on document nodes. The node-summaries RFC confirms the design intent — *"Start with file-level nodes only"* — i.e. file-level provenance is deliberate, sub-file granularity is an unbuilt proposal.
- **Constraint:** A graph.json document-node maps back to a **FILE (`source_file`), never to a 1-based line within it.** 05/ADR-005's load-bearing invariant — every `MemoryRecord.source` is `"<workRelPath>:<1-based line>"` and **MUST resolve to live text** (`src/memory/local-indexing.mjs:126/166` build `source` from a per-section heading line; the derived-index fitness function reads that line) — **cannot be satisfied by mapping graph.json document-nodes to records.** The best a graph-node→record mapping yields is `<source_file>:1` (or no line) — which fails the "resolves to a per-ADR/per-R-entry line" guarantee. The gap is exactly: graphify provenance granularity = FILE; 05 record provenance granularity = SECTION/LINE. (Whether a 0.8.44 document node ever carries an LLM-emitted line hint is live-only — assumption C1; the docs say no.)
- **Source:** `docs/how-it-works.md` (node fields = `id`/`label`/`file_type`/`source_file`); `docs/node-summaries-rfc.md` ("Start with file-level nodes only"); issue https://github.com/safishamsi/graphify/issues/1178 (`source_location` = bare line, no file qualifier); `09-RESEARCH §D`; `src/graphify.mjs:253-262`; `src/memory/local-indexing.mjs:38-52, 126, 166`.

## D. There is NO structured retrieval from graphify — `graph:query` is opaque markdown; structure means reading graph.json (answers Q3)

- **Finding:** 09/ADR-001 froze `graph:query` to `{ question, stdout, graphPath }` where **`stdout` is graphify's human markdown carried OPAQUE and parsing it is FORBIDDEN** (09-RESEARCH §C; `src/commands/graph-query.mjs:55-59` returns exactly those three fields, never a structured node/edge set). The only structured handle either query or triage returns is `graphPath` — a path to the WHOLE `graph.json`. So a `memory.backend = graphify` backend **cannot obtain `MemoryRecord`s from `graph:query`**; the only structured surface is `readGraph` + `normalizeGraph` over `graph.json` (`src/graphify.mjs:205-291`), giving `{ nodes, edges, hyperedges }` with the ADR-003 normalized shapes.
- **Constraint:** Any "graph-grounded recall" must get its STRUCTURE from the normalized `graph.json` (via a `graph:build` then `readGraph`/`normalizeGraph`), NOT from `graph:query`. The signals available there for ranking/grounding a scoped recall are: **node `community`** (Leiden clusters — relatedness grouping), **node `norm_label`** (search-normalised label), **edges with `relation`** (incl. `semantically_similar_to`, `rationale_for`) carrying **`confidence` (`EXTRACTED`/`INFERRED`/`AMBIGUOUS`) + `confidenceScore`** (preserved by `normalizeEdge`, `src/graphify.mjs:268-281`), **god-nodes** (most-connected — derivable from edge degree), and **`hyperedges`** (n-ary groupings). These are richer relatedness signals than 05's BM25-lite (`src/memory/local-retrieval.mjs:87-184`, which scores only over a record's own `text`). BUT — because nodes are file-level (Finding C) — these signals rank **files/concepts, not per-ADR/per-R-entry records.** They can ground "which work-stream FILES/topics relate to a query"; they cannot by themselves rank the section-level `MemoryRecord`s 05's contract returns. **Note also:** `graph:query` ignores the `area/stage/kind/owner/item` scope filters 05/ADR-006 makes a hard pre-filter — graphify has no notion of them.
- **Source:** 09/ADR-001 (frozen contract); `src/commands/graph-query.mjs:55-59`; `src/graphify.mjs:205-291`; `09-RESEARCH §C/§D/§H`; `src/memory/local-retrieval.mjs:64-184`.

## E. The backend interface + RecallResult/MemoryRecord are frozen and unchanged — the graphify backend MUST satisfy them byte-for-byte (the reconciliation target)

- **Finding:** The seam is fully built and frozen. A backend is a default-export `{ name, recall, reindex, status }` (05/ADR-003; `src/work-memory.mjs:35-56` registry, `:308-327` dispatch). Selection is `config.memory?.backend`, read in ONE place (`selectBackendName`, `src/work-memory.mjs:42-44`); registering `graphify` is ONE registry line + one schema enum value. `recall` MUST return `RecallResult { query, scope, records[], text }` (05/ADR-004) where each record is the frozen `MemoryRecord` with a resolving `source:line` + a numeric `score` (05/ADR-005). `brief` is COMPOSED seam-side over `backend.recall("", {item}, {limit:Infinity})` (`src/work-memory.mjs:313-321`) and `ingest` is an ALIAS of `reindex` (`:322-324`) — **neither is an interface method**, so the graphify backend implements only `recall`/`reindex`/`status` and gets `brief`/`ingest` for free. The derived-index invariant (05/ADR-001/005) is the load-bearing constraint to preserve: a fresh `reindex` reconstructs from `.md` source, holds no fact absent from it, and every `source` resolves to live text (the same guarantee `local-indexing.mjs` satisfies via per-section line numbers).
- **Constraint:** The graphify backend is **bound to produce the SAME structured `MemoryRecord`s with resolving `source:line`** that the local backend does — `renderRecallBlock` (`src/work-memory.mjs:159-167`), `briefDigest` (`:226-250`), and every consumer read `record.id/item/kind/area/title/source/recordType` and rely on `source` being a real `path:line`. graphify's graph cannot, by itself, supply that (Findings C/D). Therefore "graphify-grounded recall" cannot mean "records come FROM the graph"; the graph can only be a *ranking/relatedness signal layered onto records produced the 05 way.* The reconciliation space is enumerated in Finding F.
- **Source:** `src/work-memory.mjs:35-56, 159-167, 226-250, 308-327`; 05/ADR-003/004/005/007; `src/memory/local-indexing.mjs` (the parsers that produce resolving `source:line`).

## F. Reconciliation options (REPORTED, not chosen) — three architectures, with tradeoffs (answers Q4)

- **Finding:** Given C (graph provenance is file-level), D (no structured retrieval; structure = `graph.json`), and E (frozen `MemoryRecord` with resolving `source:line`), three viable architectures exist for "graphify-grounded recall that still yields the frozen `RecallResult` with resolving `source:line` and satisfies the derived-index invariant":

  - **(a) Records from 05's existing markdown parsers + the graph as a relatedness/ranking signal.** Reuse `parseRetrospective`/`parseArchitecture`/`buildRecords` (`src/memory/local-indexing.mjs:82-204`) to produce `MemoryRecord`s with guaranteed `source:line`; build a graph over the same work stream via `graph:build`; at `recall`, use the normalized `graph.json` (community co-membership, `semantically_similar_to` edges, god-node centrality) as an ADDITIONAL ranking/grounding signal — joining graph nodes to records by `source_file` (file-level), since that is the only key both share (Finding C). **Egress:** building the graph still egresses the work stream (Finding A) — but the RECORDS and their `source:line` come from the local parse, never from the LLM. **`source:line`:** preserved exactly (it is the 05 parser's output, untouched). **No bespoke second integration:** YES — reaches graphify only via `graph:build`/`readGraph` (the 09 commands/driver). *Tradeoff:* the graph's file-level grain means the join is coarse — it can boost/reorder records whose FILE is graph-central or graph-related to the query, but cannot distinguish two ADRs in the same file by graph signal. This is the only option where `source:line` is unconditionally safe.

  - **(b) Map graph.json document-nodes → records.** Treat each document node as a record, deriving `source` from `source_file`. **Blocked by Finding C:** document nodes carry no line, so `source` degrades to `<source_file>:1` (or no line) and FAILS the "resolves to a per-ADR/per-R-entry line" invariant; record `id/recordType/kind/area/stage/owner` (05/ADR-005's fields) are also not present on graph nodes (graphify emits `label`/`file_type`, not aof's record taxonomy). **Egress:** the records themselves come FROM the LLM extraction (Pass 3) — so the record CONTENT is LLM-summarised prose, not the verbatim source, which also strains the derived-index invariant (the record would restate a fact the LLM produced, not one traceable to a line). **Not viable** as specified unless graphify gains per-section provenance (it does not today — assumption C1).

  - **(c) Build the graph over a generated/normalized corpus of the records.** Emit one file per `MemoryRecord` (or a normalized corpus) and graph THAT, so node↔record is 1:1 and `source` is recoverable from the per-record file. **`source:line`:** recoverable only if aof maintains the record→original-`path:line` mapping itself (graphify still only knows the generated file) — i.e. aof keeps the 05 parser output as the provenance spine regardless, making the generated corpus a pure ranking artifact. **Egress:** worst case — it ships a per-record corpus (every lesson/ADR) to the LLM. **Derived-index:** the generated corpus is itself a derived artifact that must rebuild from source; adds a second derived layer to keep honest. *Tradeoff:* gives clean node↔record join but at the highest egress + the most machinery; the `source:line` guarantee still ultimately rests on the 05 parser, not the graph.

- **Constraint:** Only option (a) preserves `source:line` unconditionally and keeps records traceable to verbatim source (the derived-index invariant); (b) is blocked by file-level provenance today; (c) works only if aof keeps the 05 parser as the provenance spine anyway (so the graph is a ranking layer in (c) just as in (a), at higher cost/egress). **Across all three, building the graph egresses the work stream (Finding A)** — there is no zero-egress option; the architect's choice is between egress-for-ranking-only (a) vs egress-for-records-too (b/c). The decision is the architect's; this report only enumerates.
- **Source:** Findings A/C/D/E; `src/memory/local-indexing.mjs:82-204` (reusable parsers); `src/graphify.mjs:205-291` (the structured read); `src/commands/graph-build.mjs`.

## G. Binary-absent fallback — the seam already tolerates degrade; graphify-missing is a clean structured miss (answers Q5)

- **Finding:** Three mechanisms already exist that a `graphify` backend's `recall` can lean on. (1) `resolveGraphifyBinary()` returns a structured `{ found:false, hint }` and NEVER throws when the binary is absent (`src/graphify.mjs:86-93`, 09/ADR-004); the `graph:build`/`graph:query` commands surface it as a clear `graphify-missing` (424) error (`src/commands/graph-build.mjs:83-86`, `src/graphify.mjs:131-135`). (2) The `none` backend is the canonical empty-shaped `RecallResult { query, scope, records:[], text }` that never errors (`src/memory/none-backend.mjs:20-28`) — the exact shape a graceful degrade returns. (3) The `local` backend already degrades to an empty corpus when its index is absent/corrupt (`local-backend.mjs:21-29`, `local-indexing.mjs status` "never throws on an absent store") — and a graphify backend could, where the local index exists, fall back to local ranking (the 05 parsers + `rankRecords` are pure functions of records, reusable directly). `graph:query` also already guards the "no graph built yet" precondition with a clear `no-graph` (424) error BEFORE any spawn (`src/commands/graph-query.mjs:42-48`).
- **Constraint:** A binary-absent `recall` is a feasible graceful degrade and has at least three target shapes for the architect to choose between: **(i) none-shaped empty result** (`records:[]`, never errors — mirrors `none-backend`); **(ii) fall back to local ranking** over 05's parser output if option-(a)/(c) keeps that spine present (graph signal simply absent, records still returned with `source:line`); **(iii) the `status`/`reindex` verbs degrade like local's** (`status` reports backend + not-built, never throws). The seam itself imposes no error path — `runMemory` (`src/work-memory.mjs:308-327`) calls the backend's methods directly, so whatever the backend returns is rendered. The architect decides the target; the mechanism is available. (Whether the live binary resolves on the install host is the 09 `@manual` assumption A7, unchanged.)
- **Source:** `src/graphify.mjs:86-93, 131-135`; `src/commands/graph-build.mjs:83-86`; `src/commands/graph-query.mjs:42-48`; `src/memory/none-backend.mjs:20-38`; `src/memory/local-backend.mjs:21-29`; `src/memory/local-indexing.mjs:245-269`; 09/ADR-002/004.

## J. graphify ALREADY SHIPS a native `--backend claude-cli` that drives `claude -p` over the Pro/Max subscription with NO `ANTHROPIC_API_KEY` — the posture needs no shim (decisive for Q3)

- **Finding:** `graphify/llm.py` registers a first-class backend `claude-cli` whose doc string is verbatim: *"Routes through the locally-installed `claude` CLI (Claude Code) using `-p --output-format json`. Authenticates via the user's existing Pro/Max subscription instead of a separate ANTHROPIC_API_KEY — costs are billed to the plan, not pay-as-you-go API credit."* (`BACKENDS["claude-cli"]`, `llm.py:154-166`; `pricing {input:0,output:0}`, `default_model "claude-code-plan"`). The implementation `_call_claude_cli` (`llm.py:1074-1183`) shells out via `subprocess.run([claude, "-p", "--output-format","json", "--no-session-persistence", *add_dir_args, "--system-prompt", _extraction_system(deep)], input=user_message, text=True, timeout=_resolve_api_timeout())`, then parses the `{"type":"result"}` envelope and reads `result` + `usage.{input_tokens,cache_read_input_tokens,cache_creation_input_tokens,output_tokens}`. The dispatcher routes it (`extract_files_direct`: `if backend == "claude-cli": return _call_claude_cli(...)`, `llm.py:1363-1364`) and the keyless-backend allowlist explicitly exempts it: `if not key and backend not in ("bedrock", "claude-cli"): raise "No API key…"` (`llm.py:1341`). The CLI preflight only requires the binary on PATH, never a key: `elif backend == "claude-cli": allow_no_key = shutil.which("claude") is not None` else `error: backend 'claude-cli' requires the `claude` CLI on $PATH (install Claude Code and run `claude` once to authenticate)` (`__main__.py:4249-4258`). It has existed since ≥ 0.8.8 (`prs --triage` lists `claude-cli` among auto-detected backends, `CHANGELOG.md:357`) and is actively maintained (envelope/Windows/timeout fixes through 0.8.39+, `CHANGELOG.md:91-92, 160, 218, 226`). `GRAPHIFY_CLAUDE_CLI_MODEL` overrides the model (default is Claude Code's own default — Opus — which the comment calls "overkill"; `haiku`/`sonnet`/a full id can be set, `llm.py:1138-1145`).
- **Constraint:** The "keep extraction within Claude, no metered key" posture is **NOT a build-our-own-shim problem — it is a one-token config choice already supported upstream: `backend = "claude-cli"`.** aof's driver passes `input.backend` straight through as `--backend <value>` (`graphifyBuildArgs`, `src/graphify.mjs:113-117`), so selecting it needs **zero driver/spec change** — the aof memory-backend config (or `graph:build` input) just has to permit the literal string `"claude-cli"`. The cost is the local Claude Code install + a one-time `claude` login as a PRECONDITION (a doctor/`@manual` check, not a key in config). The sibling shim spike is therefore re-grounded: the thing it is empirically building (front `claude -p` behind extraction) is **redundant for the `claude` backend — graphify has it natively**; a shim is only warranted if the architect wants to ALSO redirect the SDK `--backend claude` path or normalise both behind one interface (Finding L).
- **Source:** `graphify/llm.py:154-166` (BACKENDS entry), `:1074-1183` (`_call_claude_cli`), `:1341` (keyless exemption), `:1363-1364` (dispatch); `graphify/__main__.py:4249-4258` (preflight); `CHANGELOG.md:357, 91-92, 160, 218, 226`; `src/graphify.mjs:113-117`.

## K. The SDK `--backend claude` call surface is a single `POST /v1/messages` (Messages API) — exact request shape a redirect target must satisfy (answers Q1)

- **Finding:** `_call_claude` (`llm.py:1005-1039`) uses the official Anthropic Python SDK: `client = anthropic.Anthropic(api_key=…, base_url=BACKENDS["claude"]["base_url"], timeout=_resolve_api_timeout())` then ONE non-streaming call `client.messages.create(model=model, max_tokens=max_tokens, system=_extraction_system(deep=deep_mode), messages=[{"role":"user","content": _anthropic_content(user_message, images)}])`. That is the **Messages API — `POST /v1/messages`, NON-streaming** (no `stream=True`; the SDK posts and blocks). Request specifics: **model** = `ANTHROPIC_MODEL` env or default `claude-sonnet-4-6` (`llm.py:65`); **max_tokens** = `BACKENDS["claude"]["max_tokens"] = 16384` resolved via `_resolve_max_tokens` (`llm.py:69, 1359`); **system** = graphify's `_extraction_system(...)` prompt (the "emit raw JSON nodes/edges" instruction); **messages** = a single user turn whose content is the concatenated file batch (text) plus, for vision, base64/data-URI image blocks. It reads back `resp.content[0].text`, `resp.usage.{input_tokens,output_tokens}`, and `resp.stop_reason` (mapped to `length` when `== "max_tokens"`). A second, lighter `messages.create` exists for community labelling (`llm.py:1874-1877`, `max_tokens≈200`). No `/v1/messages/count_tokens`, no batch API, no streaming is used.
- **Constraint:** A local redirect target for the SDK `claude` path must implement exactly **`POST /v1/messages` (non-streaming), accepting `{model, max_tokens, system, messages:[{role,content}]}` and returning a standard Messages response `{content:[{type:"text",text:…}], usage:{input_tokens,output_tokens}, stop_reason}`** — the minimal Anthropic Messages contract, nothing exotic (no tools, no streaming, no count_tokens). It must tolerate `max_tokens=16384`, a large multi-file `system`+`user` payload, and (if images are in-corpus) image content blocks. **This is the call a `claude -p`-backed shim would have to translate** — but per Finding J the `claude-cli` backend SIDESTEPS `/v1/messages` entirely (it shells the CLI, never touching the SDK), so a shim is only needed to keep the SDK `claude` path local, not the `claude-cli` path.
- **Source:** `graphify/llm.py:1005-1039` (`_call_claude` → `messages.create`), `:64-69` (claude BACKENDS: base_url, default_model `claude-sonnet-4-6`, max_tokens 16384), `:1874-1877` (labelling call); Claude Messages API (`POST /v1/messages`).

## L. `--backend claude` honours `ANTHROPIC_BASE_URL` — all SDK extraction calls can be forced to `127.0.0.1`, with a structural-safety caveat (answers Q2)

- **Finding:** The claude backend's `base_url` is read from env at import: `"base_url": os.environ.get("ANTHROPIC_BASE_URL", "https://api.anthropic.com")` and `"default_model": os.environ.get("ANTHROPIC_MODEL", "claude-sonnet-4-6")` (`llm.py:64-65`), and `_call_claude` passes that exact `BACKENDS["claude"]["base_url"]` into `anthropic.Anthropic(base_url=…)` (`llm.py:1014`). A dedicated upstream test proves it: `tests/test_anthropic_custom_endpoint.py` asserts that with `ANTHROPIC_BASE_URL=http://localhost:4000` set, `BACKENDS["claude"]["base_url"] == "http://localhost:4000"` (and the default is `https://api.anthropic.com` when unset) — the module docstring states the intent verbatim: *"point `--backend claude` at any Anthropic-compatible endpoint (LiteLLM proxy, gateways, …) without a providers.json entry."* CAVEATS: (1) it is read **at import time**, so the env must be set before graphify imports `llm` (a subprocess env, not a runtime mutation). (2) The SDK still requires a non-empty `api_key` for the `claude` backend (`ANTHROPIC_API_KEY` is the `env_key`, `llm.py:66`; without it the dispatcher raises `No API key for backend 'claude'`, `llm.py:1341-1345`) — so a redirect needs a **dummy key set** (any non-empty string) even though the call never reaches Anthropic. (3) custom OPENAI/ANTHROPIC base URLs flow through `provider_base_url_ok` (a structural URL check, `llm.py:176-197`) — a `http://127.0.0.1:<port>` loopback URL is structurally fine (unlike `OLLAMA_BASE_URL`, which hard-blocks link-local/metadata hosts, `llm.py:2014-2054`; the claude path only WARNs on non-https, it does not block loopback).
- **Constraint:** **Forcing `ANTHROPIC_BASE_URL=http://127.0.0.1:<port>` + a DUMMY `ANTHROPIC_API_KEY` in graphify's process env redirects every SDK `--backend claude` extraction call to a local shim — nothing reaches `api.anthropic.com`.** For aof this means a shim-based posture is driven purely through the **process environment the driver spawns graphify with** (the driver already controls the spawn — `spawnSync(resolved.path, args, {cwd, encoding})`, `src/graphify.mjs:138-141` — env injection is a one-line addition). The dummy-key requirement and import-time read are the two gotchas to encode. **Caveat for the architect's egress model:** redirecting to a LOCAL shim that itself calls `claude -p` does NOT make the hop on-box — the prose still leaves the machine via the Claude Code subscription to Anthropic. Locality of the SHIM ≠ locality of the EGRESS (the same distinction aof already draws for ollama in `classifyEgress`, Finding M).
- **Source:** `graphify/llm.py:64-66` (env-driven base_url/model/key), `:1014` (passed to SDK client), `:176-197` (`provider_base_url_ok`), `:1341-1345` (key required); `tests/test_anthropic_custom_endpoint.py:13-34`; `src/graphify.mjs:138-141`.

## M. `claude-cli`/shim routing is STILL an egress event, and aof's `LOCAL_BACKENDS` set does not know the value exists — a classification gap (the privacy reality for Q5)

- **Finding:** Routing extraction through `claude -p` (or a `claude -p`-backed shim) sends the same prose to Anthropic's servers that `--backend claude` would — the only thing that changes is **billing (subscription plan vs metered API credit) and auth (oauth login vs key), NOT egress.** The only genuinely on-box backend remains `ollama` (`OLLAMA_BASE_URL`, `llm.py:84`; `09-RESEARCH §F`). aof already models this correctly for egress: `classifyEgress(backend)` returns `"docs-media"` for ANY non-null backend (`src/commands/graph-build.mjs:47-48`), so a `claude-cli` build is correctly `egress:"docs-media"`. BUT aof's *reachability* helper has a blind spot: `isNetworkBackend` derives "local" from a hardcoded `LOCAL_BACKENDS = new Set(["ollama"])` and `NETWORK_BACKENDS = new Set(["claude","gemini","openai","kimi","deepseek"])` (`src/commands/graph-build.mjs:30-39`) — **neither set contains `"claude-cli"`**, so it falls through to `isNetworkBackend == true` (correct outcome — it DOES cross the network — but by accident, not by a known enumerated value), and the backend string is otherwise unmodelled in aof's contracts.
- **Constraint:** If the architect adopts `claude-cli` (or a shim), aof's privacy-classification sets are **incomplete and must be extended to KNOW the value**: `claude-cli` is network-egressing (belongs conceptually with `NETWORK_BACKENDS`, billed-to-plan being orthogonal), and a `claude -p`-backed local shim base-URL must NOT be misread as "local like ollama" (Finding L caveat). The honest framing for the architect's ADR: **`claude-cli` solves the COST/KEY-PROVISIONING problem (no pay-as-you-go key, costs on the plan) — it does NOT solve the EGRESS problem (prose still goes to Anthropic).** "Keep it all local within Claude" is true for AUTH and BILLING, false for DATA RESIDENCY; only `ollama` keeps the corpus on-box (and aof still flags it `egress:"docs-media"`, Finding 10-AA7). This is the single most important nuance to surface.
- **Source:** `graphify/llm.py:84` (ollama is the only on-box backend); `src/commands/graph-build.mjs:30-39, 47-48`; `09-RESEARCH §F`; Finding J/L.

## N. `claude -p` headless contract, output schema, and bulk-volume posture (answers Q3 detail + Q5)

- **Finding (claude -p flags/auth):** Per Claude Code headless docs: `claude -p "<prompt>"` (alias `--print`) runs non-interactively; **stdin is piped in** (graphify uses `input=user_message`, `llm.py:1148`); `--output-format {text|json|stream-json}` selects output (`json` gives `{result, session_id, total_cost_usd, usage, modelUsage, …, type:"result"}`); `--model` selects the model; `--system-prompt` REPLACES Claude Code's default agent prompt (graphify deliberately uses replace, not `--append-system-prompt`, because the default coding-agent prompt makes ~30-50% of responses come back fenced/prefaced and fail strict `json.loads` — `llm.py:1111-1118`); `--max-turns` caps turns (graphify does not set it — single-turn extraction). **AUTH: by default `claude -p` reuses the existing Claude Code oauth/subscription login** (the keychain/`~/.claude` credentials from `claude` login) — NO `ANTHROPIC_API_KEY` needed; this is the whole point. CAVEAT from the same docs: the new `--bare` mode "skips OAuth and keychain reads … authentication must come from `ANTHROPIC_API_KEY`" — so a shim/automation must NOT pass `--bare` if it wants subscription auth (graphify does not). Output envelope shape drifted: CLI ≥ ~2.1 emits a JSON ARRAY of stream events ending in a `{"type":"result"}` object; graphify's `_claude_cli_envelope` (`llm.py:1042-1071`) handles both the legacy single-object and the new-array shapes — a parser any consumer of `claude -p --output-format json` must replicate.
- **Finding (volume/cost/quality for Q5):** graphify packs files into chunks by a **token budget (default 60_000 tokens/chunk)** — `_pack_chunks_by_tokens(files, token_budget=60_000)` (`extract_corpus_parallel`, `llm.py:1700, 1747-1748`) — so the number of Pass-3 LLM calls ≈ `ceil(total_prose_tokens / 60k)` plus adaptive-retry bisections on context-overflow/hollow responses (`_extract_with_adaptive_retry`, `llm.py:1560-1607`) plus a handful of community-labelling calls batched `_LABEL_BATCH_SIZE` at a time (`llm.py:2230-2262`). For aof's work stream (tens of small `.md` files, well under one 60k chunk) this is **roughly a SINGLE extraction call + a few label calls per full build** — low volume. CRITICAL throughput caveat: `claude-cli` is **forced SERIAL** — `if backend == "claude-cli" … max_concurrency = 1` unless `GRAPHIFY_CLAUDE_CLI_PARALLEL=1` (parallel `claude -p` subprocesses "conflict over session state", `llm.py:1781-1784`), same as ollama (`llm.py:1779`). Cost posture: `claude-cli` pricing is recorded as `{input:0, output:0}` (`llm.py:160`) because spend lands on the subscription PLAN, not metered credit — vs `--backend claude` which bills the `ANTHROPIC_API_KEY` pay-as-you-go, vs `ollama` which is free + on-box. Quality: graphify defaults `claude-cli` to Claude Code's own default model (Opus-class — comment calls it "overkill for structured-JSON extraction"), so quality is high; a small local `ollama` model (`qwen2.5-coder:7b` default, `llm.py:85`) trades quality/structure-adherence for full locality.
- **Constraint:** For aof's modestly-sized work stream the LLM volume is **small (≈ one extraction chunk per build)**, so subscription-plan usage limits are unlikely to bite, and the forced-serial `claude-cli` path is acceptable at this scale (it would matter on a large code+docs monorepo, not on `wiki/work/**`). The architect's choice reduces to: **`claude-cli`** (no key, billed-to-plan, high quality, still egresses to Anthropic, serial, requires a local Claude Code install+login precondition) vs **`claude` + ANTHROPIC_BASE_URL→local-shim** (a redundant way to reach the same place unless the shim adds value, Finding J/L) vs **`ollama`** (only zero-egress option, lower extraction quality). Any consumer parsing `claude -p --output-format json` must handle BOTH the single-object and array-of-events envelope shapes (`llm.py:1042-1071`) and must NOT pass `--bare` (it would force key-auth, `code.claude.com/docs/en/headless`).
- **Source:** Claude Code headless docs (`code.claude.com/docs/en/headless` — `-p`, `--output-format json|stream-json`, stdin, `--model`, `--system-prompt` vs `--append-system-prompt`, `--max-turns`, `--bare` forces ANTHROPIC_API_KEY); `graphify/llm.py:1042-1071` (envelope parser), `:1111-1145` (system-prompt/model flags), `:1700,1747-1748` (60k token budget), `:1560-1607` (adaptive retry), `:1779-1784` (serial claude-cli), `:160` (zero-cost pricing), `:85` (ollama default model).

## O. Prior art — at least three projects already front the Claude Code SUBSCRIPTION behind a local `/v1/messages` Anthropic endpoint; reusable but thin-shim-or-native both viable (answers Q4)

- **Finding:** The exact reverse-direction prior art exists and is maintained: projects that expose the user's Claude Code/Max subscription as a LOCAL Anthropic-compatible `POST /v1/messages` server, reusing oauth (no metered key). Surveyed: **`CaddyGlow/ccproxy-api`** — "a local reverse proxy providing unified access to multiple AI providers (Claude, Codex) … using your existing subscriptions without API key billing"; supports Claude Code SDK auth via `claude /login`, default port 8000, exposes `/v1/messages`. **`rynfar/meridian`** — "bridges the Claude Code SDK to the standard Anthropic API … drop-in for any tool that supports a custom base_url"; documented usage is literally `ANTHROPIC_API_KEY=x ANTHROPIC_BASE_URL=http://127.0.0.1:3456` — the precise pattern Finding L needs (dummy key + loopback base URL). **`mergd/ccproxy`** — Claude Code oauth behind `http://localhost:8082/v1`, with fallback to the paid API on 429/403; its own README warns the approach "is hacky and may violate Anthropic's terms of service for Claude Code." (Note: the heavily-starred `raine/claude-code-proxy`, `fuergaosi233/claude-code-proxy`, `1rgs/claude-code-proxy`, `sunflower0305/claude-proxy`, LiteLLM go the OPPOSITE direction — Claude Code → OTHER models — and do NOT reuse the Claude subscription as a server; they are not the prior art for this posture.)
- **Constraint:** A shim is **build-or-reuse, both feasible** — but Finding J makes the SHIM PATH LARGELY UNNECESSARY for graphify specifically: graphify's native `claude-cli` backend already does in-process what these proxies do over HTTP, so the only reason to stand up a `/v1/messages` shim is to keep the SDK `--backend claude` path local (Finding L) or to share one endpoint across non-graphify tools. If the architect DOES want a shim, **meridian's `dummy-key + ANTHROPIC_BASE_URL=127.0.0.1` pattern is directly reusable** and matches graphify's redirect requirement exactly (Finding L). TERMS-OF-SERVICE flag: multiple prior-art READMEs warn that fronting the Claude Code subscription for non-interactive/3rd-party use may breach Anthropic's Claude Code terms — this is a POLICY risk the architect must weigh (it applies equally to graphify's own `claude-cli` backend, which is first-party but still automates the subscription); REPORTED here, not adjudicated.
- **Source:** GitHub `CaddyGlow/ccproxy-api`, `rynfar/meridian`, `mergd/ccproxy` (project READMEs/descriptions, surveyed 2026-06-22); contrast group `raine/claude-code-proxy` et al. (opposite direction). ToS caveat per the projects' own READMEs.
